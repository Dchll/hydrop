# 摘要

[修改]手机、平板和电脑之间互传文件是常见需求，但常用方式并不总是方便。云盘需要经过外网中转，蓝牙速度较慢，部分互传工具还受设备品牌限制。本文围绕 Hydrop 项目设计并实现了一套基于 Flutter 的局域网文件传输系统，主要解决同一局域网内的设备发现、文本会话、文件收发和传输状态反馈问题。系统在移动端和桌面端共用一套 Flutter 代码，状态管理使用 Riverpod，路由使用 AutoRoute，本地数据使用 Drift 保存。网络部分使用 UDP 39175 端口广播发现设备，使用 TCP 39176 端口和 FrameCodec 帧协议传输文本与文件。界面只保留设备页和设置页两个一级入口，手机端使用底部导航，桌面端使用左侧导航，并在桌面设备页中把设备列表和聊天内容并排展示。系统已经实现自动发现、文本通信、图片和文件发送、暂停取消、失败状态、通知进度以及未完成任务恢复等功能。
关键词：Flutter；跨平台；局域网传输；UDP 设备发现；TCP Socket；Riverpod

# Abstract

Moving files between phones, tablets and computers is a common task in study and office work, but common tools are not always convenient. Cloud storage depends on external networks and third-party servers, Bluetooth is often slow for large files, and some transfer tools are limited to devices from the same vendor. This thesis designs and implements Hydrop, a Flutter-based LAN file transfer system for mobile and desktop devices. The system covers device discovery, chat sessions, text messages, file transfer, progress feedback, settings management and local persistence. It uses Flutter for the shared interface, Riverpod for state and dependency management, AutoRoute for routing, and Drift for local SQLite storage. In the network layer, UDP port 39175 is used for device discovery, and TCP port 39176 with the FrameCodec protocol is used for text and file data. The application keeps two first-level entries: Devices and Settings. Mobile screens use bottom navigation, while desktop screens use side navigation and a two-column Devices page. The implemented system supports automatic discovery, two-way text communication, image and file transfer, pause and cancel operations, failure feedback, progress notifications, and interrupted transfer recovery in LAN environments.
Key words: Flutter; cross-platform; LAN file transfer; UDP device discovery; TCP Socket; Riverpod

# 1 绪论

## 1.1 研究背景

[修改]手机、平板、笔记本和台式机经常同时出现在学习和办公场景中，文件在这些设备之间来回移动也成了日常操作。比如手机拍下的课堂照片需要传到电脑整理，电脑里的文档需要发到另一台笔记本继续编辑，视频素材也可能要在平板和桌面端之间交换。这类操作通常发生在同一个 Wi-Fi 或热点环境里，用户更关心的是能不能直接发现设备、能不能快速发送、过程是否看得见。
[修改]常见的传输方式各有明显限制。云盘适合跨网络同步，但大文件要先上传再下载，速度受上行带宽影响，文件也会经过第三方服务器。蓝牙不依赖网络，但传输速度很难满足视频、压缩包这类大文件需求。厂商自带的互传工具体验较好，可是往往要求设备处在同一生态内，跨品牌设备使用时限制较多。Hydrop 选择局域网直连，正是为了避开这些限制。
[修改]局域网直传的优势比较直接：设备已经处在同一个网络内，文件不必绕到外网服务器，传输链路更短，隐私风险也更低。但传统局域网工具常要求用户查看 IP、输入端口，普通用户很容易卡在连接阶段。本文的设计重点不是只做一个 Socket 发送程序，而是把自动发现、设备列表、聊天式入口和进度反馈放在同一个应用里，让用户尽量不用理解底层网络细节。
从实际使用过程看，局域网传输应用的难点并不只在于“把文件发过去”。用户希望打开应用后就能看到设备，而不是先查看本机 IP、再手动输入对端地址；希望传输过程中能看到速度和剩余进度，而不是只看到一个无法判断状态的加载符号；希望网络断开或对端关闭应用时，界面能及时反映失败或暂停状态，而不是长时间停留在进行中。也就是说，系统需要同时处理发现、连接、传输、反馈和持久化等多个环节。若只完成 Socket 层的数据发送，而没有设备状态维护、消息状态记录和 UI 进度反馈，应用在真实场景中仍然难以使用。
跨平台也是本课题需要重点考虑的问题。移动端屏幕较窄，适合先展示设备列表，用户点击某个设备后再进入聊天页面；桌面端屏幕较宽，更适合左侧保留设备列表，右侧直接显示聊天内容。移动端还会受到应用前后台、通知权限、文件选择权限等平台机制影响，桌面端则更关注窗口尺寸变化、鼠标悬停和多列布局。本文所实现的系统没有为每个平台分别开发一套界面，而是在同一套 Flutter 工程中通过响应式窗口等级处理布局差异，使设备页、聊天页和设置页在手机和桌面端都能保持一致的功能结构。
本课题选择将设备设计成“联系人”式入口，而不是单独设计一个复杂的传输任务面板。这样做的原因是局域网文件传输往往围绕设备展开：用户通常先想到“把文件发给哪台设备”，然后才选择文本、图片、视频或普通文件。因此，设备列表承担了会话入口和状态展示的双重作用，聊天页则承载文本和附件传输。这样的组织方式降低了页面层级，也使文件传输进度能够和具体设备、具体消息自然关联起来。

## 1.2 研究目的与意义

[修改]本文以 Hydrop 应用为对象，完成设备发现、会话建立、文本消息、文件传输、状态展示和设置管理等功能。项目选择 Flutter，是因为同一套代码需要同时适配手机和桌面窗口；选择 Riverpod、AutoRoute 和 Drift，是为了把状态、路由和本地数据管理拆开。这样写出来的程序不只是一个传输 demo，而是一个可以继续扩展的跨平台应用骨架。
[修改]从使用角度看，Hydrop 可以让同一局域网内的设备自动出现在设备页，用户不用手动输入 IP 和端口。从工程角度看，项目把 Flutter UI、Dart Socket、文件流读写、系统通知和 SQLite 数据库放在同一套应用中验证。UDP 负责发现设备，TCP 负责传输数据，Riverpod 负责状态变化，Drift 负责数据保存。这些模块组合后，形成了一个比较完整的局域网传输实现。
从系统目标看，本课题并不追求把所有文件管理功能一次性做成完整网盘，而是围绕局域网内“发现设备、建立会话、发送文本和文件、展示进度、记录历史、调整设置”这一闭环展开。系统只保留设备页和设置页两个一级入口，避免把传输页、我的页、设置页分散成过多导航项。原本属于本机资料的内容被合并到设置页中，用户可以在同一位置修改本机显示名称、查看设备 ID、使用二维码连接、调整主题与语言。这样的取舍更接近当前程序的真实形态，也使论文描述和代码行为保持一致。
在工程实现层面，本文特别关注“状态可解释”。例如文本消息不是直接发送后才展示，而是先写入本地消息记录，再通过 TCP 帧发送，最后根据确认结果更新状态；文件附件也不是只显示一个文件名，而是通过附件 ID 关联进度、方向、阶段、速度和错误信息。这样即使发生超时、连接失败或用户取消，界面也能给出明确反馈。对于毕业设计而言，这类细节比单纯罗列框架更能体现系统设计和实现之间的对应关系。

本文围绕跨平台局域网文件传输场景，完成了需求分析、总体架构设计、设备发现协议设计、文本会话与文件传输实现、状态管理与本地持久化、界面设计以及系统测试等工作。具体研究内容包括以下几个方面。

# 2 相关技术介绍

## 2.1 Flutter 与 Dart

[修改]Flutter 是 Google 开源的跨平台 UI 框架。它不是简单调用各个平台的原生控件，而是通过自己的渲染体系绘制界面，所以同一套界面在手机和桌面端能保持比较一致的显示效果。Flutter 官方文档和相关英文著作对 Widget 组合、渲染机制和跨平台开发方式进行了说明[3][4][5]。在 Flutter 中，界面由 Widget 组合而成，底层再通过 Element、RenderObject 等机制完成布局和绘制。本系统需要同时适配移动端和桌面端，因此 Flutter 的组件化写法和自绘能力比较适合 Hydrop 的界面实现。
Dart 是 Flutter 的开发语言，兼具静态类型和运行时灵活性。Dart 支持 AOT 编译以保证生产环境性能，同时支持 JIT 编译与热重载以提升开发效率。Dart 语言原生支持异步编程，通过 Future、Stream、async/await 处理网络请求、文件 I/O 和数据库查询。在本系统中，UDP 广播监听、TCP Socket 通信、文件分片传输、传输进度推送等核心功能均依赖 Dart 的异步流式处理能力。借助 Stream，系统可以将设备发现、消息接收和文件进度更新统一纳入响应式数据流，减少页面层与底层 Socket 的耦合。
Flutter 的 Widget 树重建机制适合表达“状态变化后界面自动更新”的应用模型，但网络传输任务本身并不适合直接写在页面构建函数中。页面构建函数可能因主题、语言、窗口尺寸、Provider 状态变化而多次执行，如果在其中直接建立 Socket 或读写文件，容易造成重复连接和重复任务。因此，本系统将页面层和运行时能力分开：页面读取状态并触发用户意图，网络发现、TCP 服务和中断恢复由 AppRuntime、DiscoveryController、TransferServerController 和 FileTransferCoordinator 等对象完成。这样的划分可以降低 Flutter UI 重建带来的副作用。
在 UI 实现中，Flutter 的响应式布局能力也直接影响系统结构。HydropAdaptiveBuilder 根据窗口宽度划分 compact、medium、expanded 和 large 四类窗口等级。compact 和 medium 使用底部导航，expanded 和 large 使用左侧导航；设备页在桌面端使用固定宽度的设备列表和右侧聊天区域，在移动端则只显示列表并通过路由进入聊天页。这些设计不是单纯的视觉调整，而是根据不同屏幕尺寸改变信息组织方式，使同一套功能在手机和桌面端都能顺畅使用。
[修改]Hydrop 选择 Flutter 的主要原因，是项目需要同时运行在移动端和桌面端，并且界面在不同窗口宽度下要保持一致。若分别使用 Android、iOS 和桌面端原生技术开发，设备发现、聊天页、设置页和传输进度界面都要重复实现，毕业设计阶段的维护成本会比较高。Flutter 可以用同一套 Dart 代码覆盖主要平台，也可以用 Material 组件实现黑白灰、直角、2px 分割线等视觉风格。系统虽然参考了常见聊天软件的布局，但不依赖某个平台的专有控件，因此 Flutter 更适合本项目。
选择 Dart 的原因在于它与 Flutter 深度绑定，同时对异步任务支持较好。局域网传输应用不仅有页面渲染，还包含 UDP 监听、TCP 连接、文件流读写、传输进度推送和数据库 Stream 查询。Dart 的 Future 和 Stream 可以把这些异步事件组织成清晰的数据流，避免使用大量回调嵌套。项目中设备发现、消息接收、附件进度和设置变化都可以通过 Stream 或 Provider 暴露到页面，符合 Flutter 响应式 UI 的工作方式。
[修改]本文没有选择 Web 技术作为主实现，是因为 Hydrop 需要访问本地文件、监听局域网端口、显示系统通知，并把接收文件保存到下载目录。普通浏览器环境对这些操作限制较多。本文也没有选择纯原生多端开发，因为同一套功能要在多个平台重复实现，界面风格也不容易保持一致。Flutter 可以通过插件补齐文件选择、通知、路径和二维码等平台功能，同时保留一套 UI 代码，因此更符合 Hydrop 的开发目标。

## 2.2 Riverpod 状态管理

Riverpod 是 Flutter 生态中的声明式状态管理框架，其核心特点是不依赖 BuildContext，Provider 可以作为全局、类型安全的依赖容器使用[6]。系统在入口处使用 ProviderScope 包裹应用，并通过 TalkerRiverpodObserver 记录 Provider 生命周期。页面层通过 ConsumerWidget 或 ConsumerStatefulWidget 读取状态，业务层通过 Provider、NotifierProvider、StreamProvider、Provider.family 等方式暴露数据和操作。与传统依赖上下文的状态传递方式相比，Riverpod 更适合分层架构中的 repository、controller 和 service 组合。
本系统的设备列表、设置项、聊天消息、传输进度和应用运行时能力均通过 Riverpod 管理。其中传输进度采用 transferProgressStoreProvider 和 transferProgressProvider 暴露，UI 可以按附件 ID 订阅单个传输任务的方向、阶段、已传字节、总字节、速度和错误信息，避免页面直接依赖底层 Socket 回调。通过 family 形式的 provider，页面可以针对某个远端设备或附件实例精确订阅状态，从而减少不必要的重建。
[修改]Riverpod 在 Hydrop 中还承担依赖注入的作用。设备仓库、地址仓库、消息仓库、设置仓库、发现控制器、传输协调器等对象通过 Provider 暴露，页面不需要手动创建这些对象，也不需要关心它们的运行状态。以聊天页为例，页面只需要根据 remoteDeviceId 读取会话消息和传输进度，再调用 ChatPageController 完成发送、选择文件、删除消息等操作。底层到底是读取 Drift、建立 TCP 连接，还是调用 file_picker，都被封装在应用层和基础设施层中。
传输进度采用 Provider.family 的原因在于文件传输具有明显的实例粒度。一个聊天页面可能同时显示多个附件消息，每个附件都有自己的 attachmentId、方向、阶段、已传字节和速度。如果使用一个全局进度对象，任何一个附件变化都可能引起整个页面重建；如果按附件 ID 精确订阅，只有对应附件卡片需要刷新。当前程序中的 transferProgressProvider 正是按 attachmentId 暴露快照，这使聊天页附件卡片能够独立显示发送或接收进度。
[修改]Hydrop 选择 Riverpod，而不是只使用 StatefulWidget 或 InheritedWidget，是因为项目中的状态来源比较多，而且很多状态并不只属于某一个页面。设备发现来自运行时服务，消息可能来自 TCP 接收端，也可能来自用户输入，传输进度来自文件传输协调器，设置项还要被 MainApp、设置页和运行时共同读取。如果这些状态都放在页面内部，页面销毁后状态容易丢失，网络服务也会和 UI 绑定得过紧。Riverpod 可以把这些状态放到应用层，并用 Provider 管理依赖关系。
与 Provider 包相比，Riverpod 不依赖 BuildContext，适合在 Controller、Repository 和 Service 中组合依赖。文件传输协调器需要访问消息仓库、地址仓库、通知服务和进度存储；发现控制器需要访问广播服务、设备仓库和地址仓库。这些对象并不天然处于 Widget 树中，使用 Riverpod 可以减少通过构造函数层层传递依赖的样板代码。对于毕业设计项目来说，这种依赖管理方式也能更清楚地体现分层架构。
[修改]Riverpod 的另一个选型原因是方便测试和替换实现。设备列表、会话消息和设置项都可以通过 Provider 暴露，测试或调试时可以替换仓库或状态来源。虽然本论文不把大量测试代码放入正文，但从工程结构看，Provider 化的依赖比全局单例更容易控制，也更适合后续增加自动化测试。

## 2.3 AutoRoute 路由管理

AutoRoute 是 Flutter 的声明式路由框架，通过 @RoutePage 注解和代码生成实现类型安全的路由导航[7]。本系统使用 AppRouter 管理页面路由：AppRoute 是应用主壳，内部包含 HomeRoute 和 SettingsRoute 两个一级子路由；ChatRoute 是从设备页进入的会话路由，携带远端设备 ID 与显示名称。该设计使一级页面保持简洁，也使聊天页能够根据设备上下文渲染消息时间线。AutoRoute 的参数校验和嵌套路由能力也保证了响应式布局切换时页面栈的可预测性。
[修改]系统使用 AutoRoute，主要是因为聊天页必须带着设备上下文进入。ChatRoute 需要 remoteDeviceId 和 displayName 两个参数，前者用于读取对应设备的消息和附件，后者用于页面标题等显示。如果用字符串路径手动拼接参数，很容易漏传或写错字段。AutoRoute 通过生成代码检查路由参数，缺少必要参数时会在开发阶段暴露问题，比进入页面后才发现设备上下文为空更可靠。
一级导航采用 AutoTabsRouter，也是因为设备页和设置页属于主壳内部的两个稳定入口。移动端使用底部导航，桌面端使用左侧导航，但二者对应的路由栈是一致的。AutoRoute 可以把主壳路由、子路由和独立聊天路由组织在同一个 AppRouter 中，减少手动维护 Navigator 的复杂度。对于当前只保留两个一级 tab 的产品形态，这种路由结构足够清晰，也为后续恢复更多入口保留了扩展空间。

## 2.4 Drift 本地数据库

Drift 是 Dart/Flutter 的类型安全响应式数据库框架，基于 SQLite 构建[8][9]。系统通过 Drift 定义 8 张业务表：设备表、设备地址表、连接会话表、设置表、本机资料表、消息表、消息附件表和统计表。Drift 的 Stream 查询能力使页面可以直接监听数据库变化并自动刷新列表，而无需手动轮询。数据库 schemaVersion = 1，处于第一版开发阶段，不包含升级迁移逻辑；首次创建数据库时调用 migrator.createAll() 创建全部表，并额外创建设备地址唯一索引、消息本地 ID 唯一索引和附件 ID 唯一索引。
[修改]Hydrop 选择 Drift 和 SQLite，而不是 Hive、SharedPreferences 或普通文件存储，是因为项目数据之间有明确关系。对端设备和设备地址是一对多关系，消息和附件也是一对多关系，连接会话、设置项、本机信息和统计信息还需要分别保存。如果使用键值存储，查询某台设备的消息、某条消息的附件或某个地址的可达状态会比较零散；如果使用 JSON 文件，重复写入和并发更新也不好处理。SQLite 适合保存这类结构化数据，Drift 则为 Dart 项目提供类型安全的表定义、查询和 Stream 监听。
[修改]Drift 的响应式查询与 Hydrop UI 模型比较契合。设备发现控制器写入设备表后，设备页可以自动刷新；接收端写入消息表后，聊天页可以自动出现新消息；设置页修改主题或语言后，MainApp 可以读取设置并更新界面。若直接使用 sqlite3 手写 SQL，也能实现这些功能，但需要手动维护查询结果到 UI 的同步。Drift 把表结构、DAO、数据类和 Stream 查询整合到一起，减少了这部分重复工作。
[修改]数据库版本保持 schemaVersion = 1，是因为项目仍处于第一版开发阶段。开发过程中表结构变化较快，旧数据可以通过清理应用数据后重新创建，不必为尚未稳定的结构维护复杂迁移脚本。等系统进入稳定发布阶段，再补充从旧版本到新版本的迁移逻辑会更合适。论文按当前代码描述首次创建数据库和 schemaVersion = 1，可以避免把未实现的迁移功能写成已经完成的内容。

## 2.5 网络通信

局域网通信和 Socket 编程的基础理论可参考 UNIX 网络编程与计算机网络相关文献[10][11]。UDP 适用于局域网设备发现等对实时性要求较高、允许少量丢包的场景[12]。本系统使用 RawDatagramSocket 在 UDP 39175 端口监听并接收设备广播，广播 payload 类型为 hydrop.discovery.hello，协议版本为 1，内容包含设备 ID、显示名称、TCP 端口、能力列表、nonce 和地址列表等信息。广播间隔为 10 秒，设备 TTL 为 12 秒，TTL 扫描间隔为 3 秒。
[修改]TCP 适合用来传输文本消息和文件数据。它本身提供连接管理、可靠传输和顺序保证，这些都是大文件传输需要的基础[13]。Hydrop 的传输服务默认使用 TCP 39176 端口，数据不采用按行分隔的文本协议，而是采用 FrameCodec 帧协议：4 字节 header 长度、4 字节 body 长度、JSON header 和 binary body。文本消息、文件 offer、文件分片、完成确认、心跳和错误消息都通过同一种帧结构传输，协议更容易维护和扩展。发现广播间隔和异常处理也参考了 UDP 使用建议中关于拥塞控制和报文健壮性的要求[14]。
本系统将 UDP 和 TCP 的职责分开。UDP 只负责低成本发现，广播 payload 中携带设备 ID、显示名称、TCP 端口、能力列表、nonce 和地址列表，接收方据此更新设备和地址记录。TCP 负责可靠传输，文本消息、文件 offer、分片、完成确认、心跳和错误信息都通过 TCP 帧传递。这样的划分可以避免用 UDP 承担大文件传输带来的可靠性问题，也避免每次发送文件前都要求用户手动输入地址。
[修改]FrameCodec 的设计重点是解决 TCP 字节流边界问题。TCP 面向字节流，不保证一次读取正好对应一次应用层消息；如果直接用换行符或字符串拼接协议，遇到二进制文件内容时容易出现边界不清或转义复杂的问题。因此系统在每个帧前放置 header 长度和 body 长度，接收端先读取长度，再读取对应数量的 header 和 body。header 使用 JSON 保存帧类型、协议版本、消息 ID、附件 ID、文件名、偏移量等元数据，body 用于存放文本内容或文件分片二进制数据。这样既保留了元数据的可读性，也减少了文件内容编码转换的开销。
[修改]设备发现选择 UDP 广播，是因为发现阶段只需要让局域网中的设备知道“我在这里”，不需要为每台未知设备预先建立连接。UDP 广播实现成本低，适合周期性发送较小的公告 payload。即使少量广播丢失，下一轮广播仍可刷新设备状态。若发现阶段使用 TCP，系统必须知道对端地址才能连接，这与“自动发现附近设备”的目标相冲突。若依赖中心服务器，又会失去局域网直传不经过外网的特点。
[修改]数据传输选择 TCP，是因为文本消息和文件分片需要按顺序、可靠地到达对端。如果文件分片乱序、丢失或重复，应用层就需要处理更多异常情况。TCP 已经提供可靠传输和顺序保证，适合作为文件传输的基础协议。系统在 TCP 之上仍然设计 fileOffer、fileChunk、fileComplete 和 ACK，是为了表达应用层含义，例如接收端是否同意接收文件、某个附件已经传了多少、文件完成后是否校验成功。这些信息不是 TCP 自身直接提供的。
FrameCodec 选择“JSON header + binary body”的原因是兼顾可读性和效率。header 中的帧类型、版本、附件 ID、文件名和 offset 适合用 JSON 表达，调试时也容易查看；body 中的文件分片必须保持二进制，不适合再转成 Base64 或字符串。若整个帧都使用 JSON，文件内容会膨胀并增加编码成本；若整个帧都使用自定义二进制结构，调试和后续扩展字段会更麻烦。当前结构在毕业设计阶段更容易说明，也更贴近工程实践。
[修改]文件分片大小选择 1MB，是在传输效率和内存占用之间折中。分片过小会增加帧数量和 ACK 次数，降低大文件传输效率；分片过大则会增加单次内存占用和错误重试成本。1MB 分片可以减少帧数量，同时防止一次性占用过多内存。最大文件大小设置为 16GB，是为了防止用户误选极端大文件造成磁盘、内存和长时间连接风险；并发传输上限设置为 2，是为了防止多个大文件同时争抢网络和磁盘资源。

## 2.6 数据序列化与不可变数据

[修改]系统使用 json_serializable、freezed、drift_dev、riverpod_generator、auto_route_generator 等代码生成工具减少样板代码。发现 payload、二维码连接 payload、消息状态、数据库表映射和 Provider 声明均通过类型安全方式组织，使协议解析、状态变更和持久化代码在编译阶段就可以获得检查。结构化数据建模与持久化设计也符合数据密集型应用中对数据模型清晰性和演进功能的要求[15]，同时也与软件工程导论中强调的分层、模块化和阶段化开发思想相一致[16]。数据结构教材中关于抽象数据类型、线性表、树和图的组织方式，也为系统消息、附件和设备地址等对象建模提供了基础方法[17]。
选择 json_serializable 的原因是发现 payload、二维码 payload 和部分协议字段都需要在 Dart 对象和 JSON 之间转换。手写 fromJson 和 toJson 容易漏字段或写错类型，尤其在 payload 字段不断调整时维护成本较高。json_serializable 可以根据模型生成序列化代码，使协议字段和 Dart 类型保持一致。对于 UDP 发现这种需要过滤协议版本、设备 ID、端口和地址列表的场景，类型明确比临时 Map 操作更可靠。
[修改]选择 freezed 的原因是状态模型经常需要不可变复制。传输进度快照、消息状态和设置状态在 UI 中频繁变化，如果直接修改同一个可变对象，页面是否重建、状态是否被意外覆盖都不容易判断。不可变对象配合 copyWith 可以清楚表达“基于上一状态生成下一状态”的过程，也更适合 Riverpod 的状态更新方式。虽然不可变建模会增加一些生成代码，但可以减少手写相等判断和复制逻辑。

## 2.7 日志与可观测性

[修改]系统使用 Talker 记录日志，并通过 TalkerRiverpodObserver 观察 Provider 的创建、更新、销毁和失败事件。网络发送链路中的关键错误会输出中文日志，并带有统一标志符，方便开发时检索。通过这些日志，可以更快定位设备发现、TCP 建连、消息确认、文件发送和文件接收中的问题。
选择 Talker 的原因是它可以同时覆盖普通日志、错误日志和 Riverpod 生命周期观察。局域网传输问题常常与设备、路由器、权限、端口和对端状态有关，仅靠 UI 提示很难判断失败位置。通过 Talker 记录发现、连接、发送、接收、确认和失败信息，开发者可以在控制台中按统一标志符检索链路问题。日志使用中文，是为了在毕业设计开发和调试过程中更快定位问题，不需要反复翻译错误含义。
日志不会替代用户提示。普通用户看到的是附件卡片的失败状态、应用内提示或 toast；开发者看到的是设备 ID、消息 ID、附件 ID、文件名和异常栈。选择这种分层反馈方式，是因为底层异常对普通用户没有直接帮助，但对调试很重要。Talker 与 Riverpod Observer 结合后，还能观察 Provider 是否频繁创建和销毁，帮助排查页面重建和状态生命周期问题。

## 2.8 平台能力插件

系统使用 network_info_plus 与 dart:io 枚举本机网络信息，使用 path_provider 获取应用支持目录和下载目录，使用 file_picker 进行文件选择与保存，使用 qr_flutter 和 mobile_scanner 实现二维码展示与扫描，使用 flutter_local_notifications 显示传输进度通知，使用 fluttertoast 在移动端显示临时提示，并在桌面端使用应用内提示组件进行反馈。这些插件分别承担网络诊断、文件系统定位、文件选择、二维码连接、系统通知、临时提示、网络图片缓存、外链跳转、本地视频播放和 HTTP 请求等平台相关能力，使业务逻辑无需直接依赖平台原生代码。
平台插件的选型原则是尽量使用 Flutter 生态中职责单一、跨平台支持较明确的库。file_picker 被用于文件选择和保存，是因为系统需要从用户选择的真实文件路径读取内容，并在必要时调用平台文件选择器；path_provider 被用于获取下载目录和应用目录，避免手写不同平台的路径规则；flutter_local_notifications 被用于传输进度通知，是因为大文件传输可能持续较久，用户切到后台后仍需要看到状态。
二维码能力选择 qr_flutter 和 mobile_scanner，是因为二维码连接包含展示和扫描两个方向。qr_flutter 负责在本机生成连接二维码，mobile_scanner 负责调用摄像头识别对端二维码。自动发现依赖 UDP 广播，在部分网络环境下可能受到限制，二维码连接可以作为补充入口。二维码内容经过精简，只携带连接所需的核心字段，既减少扫描难度，也降低展示区域对设置页布局的压力。
移动端提示选择 fluttertoast，桌面端使用应用内提示，是因为移动端用户更习惯短时浮层反馈，而桌面端 toast 体验和平台一致性较弱。通知、toast 和应用内提示都只是反馈渠道，不参与传输协议本身。因此插件初始化失败不能让文件传输失败，应用层需要捕获这些平台异常并把它们限制在反馈模块内。

## 2.9 代码生成工具链

项目使用 build_runner 作为统一的代码生成执行器，配合 auto_route_generator、drift_dev、freezed、json_serializable、riverpod_generator 和 flutter_gen_runner 使用。代码生成覆盖路由、数据库、状态模型、资源引用和 Provider 声明，减少重复代码并提高类型安全性。
本系统选择代码生成工具链，是因为项目中存在大量结构化声明。路由需要生成强类型参数类，数据库需要生成表映射和 DAO 支持，JSON 模型需要生成序列化代码，Riverpod 注解需要生成 Provider，资源文件需要生成类型安全引用。如果全部手写，代码量会明显增加，而且字段名、路由名和资源路径都容易写错。build_runner 作为统一入口，可以让这些生成任务集中执行，保持工程构建方式一致。
代码生成的代价是需要维护生成文件和构建步骤，但对于本系统来说收益更大。设备发现 payload、数据库表和路由参数都属于容易随着需求变化而调整的结构，生成代码可以在编译阶段暴露不一致问题。例如 ChatRoute 参数变化后，未传 remoteDeviceId 或 displayName 的调用点会报错；数据库字段变化后，DAO 和数据类也会随生成结果更新。这种早暴露错误的能力有助于减少运行时问题。

# 3 系统需求分析

本章采用面向对象分析方法描述系统需求，不使用结构化方法中的数据流图，也不把已经实现后的页面点击过程画成业务流程图。开发类课题的需求分析应先识别系统边界、参与者、用例和领域对象，再进入后续设计。用例分析用于说明用户与系统之间的目标关系，领域对象分析用于提炼问题域中的核心概念；具体类职责、对象交互、状态变化和部署关系放在第 4 章设计部分展开。UML 建模和面向对象分析设计的基本方法可参考相关研究[18][19]。

## 3.1 系统边界与参与者分析

[修改]Hydrop 的系统边界是“Hydrop 局域网文件传输应用”。系统内部负责设备发现、会话消息、文件传输、传输进度、本机信息和设置管理；系统外部包括使用应用的用户、局域网中的对端设备、操作系统文件系统、系统通知服务、二维码扫描/展示功能以及本地数据库。系统不依赖云端中转服务器，通信对象限定为同一局域网内可达设备。
[修改]系统主要参与者包括普通用户、对端设备、操作系统和本地数据库。普通用户发起发现、选择设备、发送文本、选择文件、暂停或取消传输、修改设置；对端设备接收发现广播、建立 TCP 连接、回复消息确认和文件确认；操作系统提供文件选择、下载目录、通知权限、网络接口和应用运行状态；本地数据库负责保存设备、地址、会话、消息、附件和设置。
普通用户与系统的交互集中在设备页、聊天页和设置页三个位置。设备页承担设备发现结果展示和进入会话的入口，用户不需要理解 IP 地址、端口和网卡信息；聊天页承担文本与文件传输，用户只需要面对消息气泡、附件卡片和输入栏；设置页承担本机资料与全局偏好，用户可以直接修改本机显示名称，切换语言和主题。这样的边界划分使网络细节留在系统内部，用户面对的是更接近即时通信软件的操作路径。
对端设备虽然不是“人”，但在系统分析中属于重要外部参与者。它会接收本机 UDP 广播，也会向本机发送广播；它可能作为文件接收端，也可能作为发送端；它需要在收到文本消息、文件 offer、分片和完成帧时返回对应确认。若对端设备关闭应用、离开局域网或端口不可达，本机需要通过 TTL、连接超时和确认超时等机制更新状态。由此可见，对端设备并不是简单的数据目标，而是一个具有协议状态的协作对象。
操作系统参与者提供了跨平台应用无法自行完成的能力。文件选择依赖系统选择器，下载目录依赖平台路径服务，通知展示依赖系统通知权限，移动端应用前后台切换也由操作系统驱动。系统设计时不能假定这些能力永远可用，因此通知插件失败不应阻断文件传输，文件选择取消不应创建空附件，应用进入后台后也不应继续保持高频发现。将这些能力视为外部参与者，有助于在需求阶段提前识别边界条件。

## 3.2 用例分析

## 3.3 功能需求

[修改]在设备发现需求中，系统应在应用启动和前台恢复时启动局域网发现功能。本机需要周期性广播设备 ID、显示名称、TCP 端口、功能列表、nonce 和地址列表；同时监听同一端口上的对端广播。系统收到对端设备广播后，应保存或更新设备表和设备地址表，并根据 TTL 将长时间未刷新的设备置为离线状态。设备页应展示设备名称、连接状态、测速摘要和最后一次传输时间；在线设备使用正常文本颜色，不在线设备置灰。
[修改]在会话通信需求中，系统应支持用户从设备页进入指定设备会话。会话页面需要根据对端设备 ID 读取本地消息时间线，支持文本消息发送和接收。文本发送时应先创建本地消息记录，再通过 TCP 帧协议发送到对端设备；发送成功后更新为已发送，失败时保留错误信息，方便用户重试或判断问题。
[修改]在文件传输需求中，系统应支持用户选择图片、视频和普通文件作为聊天附件发送。发送端需要在传输前检查文件大小，创建附件消息，选择远端可连接地址，建立 TCP 连接，发送文件 offer，并按 1MB 分片传输。接收端优先把文件保存到下载目录中的 Hydrop 文件夹；如果平台不能提供下载目录，则使用应用支持目录作为兜底位置。传输过程中应显示已传字节、总字节、速度、阶段和错误信息，并提供暂停和取消功能。
[修改]在设置管理需求中，系统应提供设置页作为一级入口，整合本机信息和配置功能。用户可以直接在页面上修改本机显示名称，查看设备 ID、二维码连接、本地 IP 和诊断信息；可以切换浅色、深色或跟随系统主题；可以切换跟随系统、英文、简体中文和繁体中文；可以配置传输加密开关和自动恢复传输开关。
[修改]在数据持久化需求中，系统应将设备、地址、连接会话、设置、本机信息、消息、附件和统计信息保存到本地数据库。消息和附件记录应支持按对端设备查询；设备地址应防止同一设备、同一 IP、同一端口重复写入；附件 ID 和本地消息 ID 应具备唯一性，防止发送或接收重试时产生重复记录。
[修改]设备发现功能需要满足“自动、可恢复、不过度打扰”的要求。自动是指应用进入前台后能主动发送广播并监听对端广播；可恢复是指短时间网络抖动不会立即删除设备，而是通过 TTL 将地址标记为不可达；不过度打扰是指发现过程不应频繁弹窗或要求用户确认。设备页只展示设备名称、速度摘要、最后一次传输和在线状态，不在线设备通过灰色文本区分。这样用户可以快速判断哪些设备可用，而不需要阅读底层网络日志。
[修改]文本消息功能需要满足“可见、可追踪、可失败”的要求。用户发送文本后，消息应立即进入本地时间线，而不是等待网络确认后才出现；消息发送过程中需要有 pending 或 sending 状态，确认成功后进入 sent，失败后进入 failed。失败消息不应直接消失，因为消失会让用户无法判断是没有点击成功，还是网络发送失败。保留失败状态也方便后续加入重试、复制错误信息或诊断提示。
[修改]文件传输功能需要考虑大文件场景。系统应防止使用一次性 readAsBytes 的方式读取大文件，而应按分片流式读写；接收端优先把文件保存到下载目录中的 Hydrop 文件夹，方便用户在系统文件管理器中找到，下载目录不可用时再退到应用支持目录。传输过程中应展示速度、已传字节、总字节和阶段状态。对于暂停、取消和失败，UI 应把状态落到具体附件消息上，而不是只显示一个全局提示，用户可以在聊天记录中回看某个文件是否成功传输。
[修改]设置管理功能需要和系统运行时关联。主题和语言属于界面偏好，修改后应通过 Provider 推送到 MainApp 并即时生效；本机显示名称属于发现 payload 的一部分，修改后会影响对端设备列表中的名称；自动恢复传输开关影响应用启动时是否尝试恢复未完成任务；传输加密开关虽然在当前阶段主要作为设置入口保留，但它在数据库中已有字段，方便后续接入真正的加密传输。

## 3.4 非功能需求

[修改]在性能要求上，文件传输不能把大文件一次性读入内存，而是使用文件流按分片读写。系统分片大小为 1MB，单文件大小上限为 16GB，并发传输上限为 2。传输进度通过 Riverpod 推送到界面，附件卡片可以按附件 ID 单独订阅进度，减少无关页面的重建。
[修改]在稳定性要求上，系统需要处理网络异常、协议解析失败、连接中断、确认超时、文件过大、通知插件失败和数据库唯一约束冲突等情况。传输过程中应支持暂停、取消、失败状态显示和中断恢复。应用切到后台或回到前台时，发现服务和传输服务也要跟随调整，防止后台连接状态和界面显示不一致。
[修改]在安全性要求上，系统以局域网直连为基础，文件不经过外部服务器。设置表中保留传输加密开关，为后续协议加密提供设置入口；文件传输链路保留 SHA-256 校验字段，用于完整性验证，相关哈希算法标准可参考安全哈希标准文档[20]。
在可维护性方面，系统应采用清晰的分层结构。页面层只负责渲染和交互，状态层负责组织 UI 状态，数据层负责数据库访问，网络与平台基础设施层负责 Socket、文件系统、通知和二维码能力。模块之间通过 Provider、Controller、Repository 和 Service 协作，避免页面直接操作数据库或 Socket。
在可扩展性方面，发现 payload、FrameCodec header 和数据库表字段均采用结构化设计。系统应能够在不破坏已有功能的前提下扩展新的能力标识、传输阶段、附件类型、加密字段和统计字段。
[修改]系统需要保留可追踪的运行日志。局域网传输问题不一定每次都能复现，原因可能是网络隔离、路由器限制广播、系统权限不足、端口被占用，或者对端应用已经关闭。如果没有日志，开发者只能根据界面现象猜测问题。项目在消息发送链路中使用中文日志和统一标志符记录关键错误，可以区分地址选择失败、TCP 建连失败、确认超时、文件过大和通知初始化失败等情况。日志不直接给普通用户看，但能提高开发和调试效率。
兼容性也是非功能需求的一部分。系统面向移动端和桌面端，不能只按单一平台设计。移动端更容易出现键盘弹起、应用后台、通知权限不足等问题；桌面端更容易出现窗口尺寸变化、鼠标悬停、侧边导航空间占用等问题。因此 UI 设计采用直角、黑白灰、2px 分割线和响应式布局，避免依赖复杂背景和固定尺寸。弹窗统一采用 bottom sheet，也是为了减少 AlertDialog 在不同窗口宽度下的尺寸问题。

## 3.5 领域对象分析

需求分析阶段需要抽取问题域对象，为设计阶段的类图提供依据。本系统的问题域对象主要包括本机资料、远端设备、设备地址、连接会话、消息、消息附件、传输任务、传输进度和系统设置。它们之间的关系是：一个远端设备可以拥有多个设备地址；一个远端设备可以对应多条消息；一条消息可以关联多个附件；一个附件可以对应一个传输任务和一个传输进度快照；系统设置和本机资料属于本机全局状态。

需求分析阶段抽取出的主要问题域对象不涉及 Flutter Widget、数据库 DAO 等实现类。LocalProfile 表示本机资料，RemoteDevice 表示远端设备，DeviceAddress 表示设备地址，ConnectionSession 表示连接会话，ConversationMessage 表示会话消息，MessageAttachment 表示消息附件，TransferTask 和 TransferProgress 表示传输任务与进度，AppSettings 表示系统设置。对象之间的核心关系包括：一个远端设备对应多个设备地址，一个远端设备对应多条会话消息，一条会话消息可以关联多个附件。
这些领域对象与数据库表并非完全一一对应，但它们之间存在稳定映射。RemoteDevice 主要落到 device_items，DeviceAddress 落到 device_address_items，ConversationMessage 落到 message_items，MessageAttachment 落到 message_attachment_items，AppSettings 落到 setting_items，LocalProfile 落到 mine_items。TransferProgress 在 UI 中以 Riverpod 快照形式高频变化，同时将关键进度和终态写回附件表。这样的设计说明系统既有持久化对象，也有运行时对象，不能把所有状态都简单理解为数据库字段。
领域对象分析还帮助确定页面组织方式。RemoteDevice 是用户选择会话的入口，所以设备页以设备列表为中心；ConversationMessage 和 MessageAttachment 是聊天页展示的主体，所以聊天页按照消息时间线组织；AppSettings 和 LocalProfile 都属于本机全局状态，所以设置页整合本机资料和偏好设置。这样从需求对象到页面结构之间形成了对应关系，避免页面设计只凭视觉风格决定。

# 4 系统设计

[修改]本章使用 UML 面向对象设计方法说明系统结构与交互。需求分析阶段主要说明用户目标和系统边界，设计阶段则可以说明系统内部类、组件、对象调用和状态变化。本章不使用数据流图，也不把页面点击路径当成业务流程图，而是按 UML 的思路说明静态结构、动态交互、状态迁移和部署关系。

## 4.1 总体架构设计

[修改]Hydrop 使用表现层、应用状态层、数据访问层、网络与平台基础设施层的分层架构。这样划分是为了把页面、状态、数据和平台功能分开。表现层只负责页面显示和用户操作，不直接操作 Socket、数据库和文件系统；应用状态层通过 Riverpod 管理设备、聊天、传输、设置和应用运行状态；数据访问层通过 Repository 和 DAO 读写 Drift 数据库；网络与平台基础设施层封装 UDP、TCP、文件系统、通知、二维码、日志和平台插件。
从依赖方向看，表现层依赖应用状态层提供的 Provider 和 Controller，应用状态层依赖 Repository 与 Service，Repository 依赖 DAO，DAO 依赖数据库连接。底层模块不反向依赖页面，这样可以避免 UI 变化影响网络协议和数据存储逻辑。系统运行时由 AppRuntime 统一协调发现服务、TCP 传输服务、通知权限和中断传输恢复，避免各页面分别启动网络能力而造成重复监听、状态竞争或资源泄漏。
[修改]系统按照业务职责划分为设备发现、会话消息、文件传输、设置管理、本机信息和持久化统计六类主要功能。设备发现模块负责发现局域网内可达设备并维护在线状态；会话消息模块负责文本消息的创建、发送、接收和状态变化；文件传输模块负责文件 offer、分片传输、进度反馈、暂停取消和完成确认；设置模块负责主题、语言、传输偏好和本机显示名称；持久化模块负责设备、地址、会话、消息、附件和统计数据落库。这样的划分保证各模块职责边界清晰，方便后续扩展加密传输、传输队列、缩略图生成等功能。
[修改]架构设计还要处理跨平台资源管理问题。移动端和桌面端在后台网络、通知权限、文件目录和窗口尺寸上的规则并不完全一样，所以系统没有把发现服务和传输服务绑定到某一个页面，而是交给运行时层管理。页面进入或离开不直接决定 Socket 的创建和释放；应用前台、后台状态变化才是网络服务启动和停止的主要依据。这样可以减少页面重建带来的副作用，也能让设备页、聊天页和设置页共享同一份运行状态。
[修改]系统不设置中心服务器，每台设备都同时具备发现者、被发现者、发送端和接收端身份。这种对等结构使系统部署更简单，但也要求本地节点保存足够的设备、地址和消息状态。为此，系统将短期状态和长期状态分开管理：传输进度、页面选择、输入框内容等短期状态主要保存在 Riverpod 状态树中；设备记录、地址记录、消息记录、附件记录和设置项等长期状态写入 Drift 数据库。短期状态用于提高界面响应速度，长期状态用于应用重启后的恢复和历史记录展示。
[修改]这种分层设计可以减少界面变化对底层逻辑的影响。后续如果要增加新的传输协议、设备信息字段或页面模块，可以优先在对应层中修改，而不是让页面层直接依赖网络和存储细节。这样新增功能时影响范围更小，也更容易保持其他模块稳定。

系统各层组件之间保持自上而下的依赖关系。Presentation 层包含 AppPage、HomePage、ChatPage、SettingsPage，负责界面展示与用户操作入口；Application 层包含 AppRuntime、DiscoveryController、ChatPageController、FileTransferCoordinator、TransferServerController 和 TransferProgressStore，负责业务编排和状态暴露；数据层包含 Repository、DAO 和 AppDataBase，负责持久化访问；基础设施层包含 DiscoveryBroadcastService、DiscoverySocketService、FrameCodec、本地文件服务、通知服务和二维码服务，负责平台与网络能力封装。

## 4.2 静态类结构设计

系统的静态类结构以 Controller、Repository、Service 和 Entity 为核心。Controller 负责业务编排，Repository 负责业务数据读写，Service 负责底层能力封装，Entity 或 Table Model 表示持久化对象。表现层页面只依赖 Provider 暴露的状态和控制器方法，不直接依赖 Socket 或 Drift 查询对象。
AppRuntime 是运行时总协调对象，负责根据应用生命周期启动或暂停发现服务和 TCP 服务，并在应用恢复到前台时触发中断传输恢复。DiscoveryController 是设备发现的业务控制器，它接收广播服务解析后的远端设备信息，完成本机过滤、nonce 去重、设备表更新、地址表更新和 TTL 扫描。ChatPageController 是聊天页的业务入口，负责文本消息发送、文件选择后的附件消息创建、失败重试和消息删除。FileTransferCoordinator 是文件传输的核心编排类，负责地址选择、TCP 建连、文件 offer、分片读写、进度上报、暂停取消和完成确认。TransferServerController 则负责接收对端 TCP 连接、解析帧类型并分发文本消息、文件传输、心跳和测速请求。
Repository 层用于屏蔽 Drift 表结构和查询细节。设备仓库负责设备基础信息和连接状态；地址仓库负责多地址历史、可达性和测速结果；消息仓库负责会话消息和附件记录；设置仓库负责主题、语言、传输加密和自动恢复设置；本机资料仓库负责本机显示名称和设备 ID。Service 层面向技术能力，例如 UDP 广播发送、UDP 监听、TCP 连接、FrameCodec 编解码、通知展示和文件系统路径管理。通过这些类型的组合，系统实现了“页面只表达意图，控制器编排业务，仓库管理数据，服务封装技术”的结构。
[修改]在对象关系上，RemoteDevice 是会话、地址和传输围绕的主要对象。设备 ID 是对端设备在本机数据库中的稳定标识，聊天消息通过 remoteDeviceId 关联设备，设备地址通过 deviceId 关联设备，附件通过 messageId 关联消息。文件传输时，系统不直接把文件路径当作任务身份，而是使用 attachmentId 标记一次附件传输。这样同一个附件在界面、数据库、通知和进度状态中都能对应起来，也能减少只靠文件名带来的冲突。
[修改]页面类不负责保存领域数据，也不直接处理网络协议。HomePage 负责展示设备列表和桌面端双栏聊天区域，ChatPage 负责展示某一设备的会话，SettingsPage 负责展示本机信息和全局设置。页面中的点击、长按、输入、选择文件等事件会转换成 Controller 方法调用。Controller 再决定是否查询地址、创建消息、发送帧、更新数据库或报告错误。这样页面代码更接近界面描述，业务判断集中在应用层，后续调整 UI 样式时不用修改协议和数据库逻辑。

系统核心类之间的职责划分和依赖方向较为明确。AppRuntime 聚合 DiscoveryController、TransferServerController 和 FileTransferCoordinator，用于统一协调应用运行期网络能力；DiscoveryController 依赖广播发送服务、广播接收服务、设备仓库和地址仓库，负责发现链路；ChatPageController 依赖消息仓库、地址仓库和文件传输协调器，负责会话操作；FileTransferCoordinator 依赖消息仓库、地址仓库、传输通知服务、传输进度存储和 FrameCodec，负责文件传输编排；Repository 依赖 DAO，DAO 依赖 AppDataBase。

## 4.3 动态交互设计

[修改]设备发现、文本消息发送和文件传输是系统中最重要的三个动态交互场景。这里分析的是对象之间的调用顺序，而不是用户在页面上的点击路线，这更符合面向对象开发类论文的写法。系统在动态交互上遵循两个原则：一是用户操作先转化为 Controller 方法调用，再由 Controller 调用 Repository 和 Service；二是会影响界面的结果都写入数据库或 Riverpod 状态，再由 Provider 推送到页面。

设备发现过程采用运行时统一启动、控制器统一处理、页面订阅状态变化的方式。应用进入前台后，AppRuntime 调用 DiscoveryController 启动发现流程；DiscoveryController 启动 DiscoveryBroadcastService 和 DiscoverySocketService，前者周期性发送本机公告，后者监听并解析对端公告；DiscoveryController 对收到的 payload 进行本机过滤和 nonce 去重，随后通过 DeviceRepository 与 DeviceAddressRepository 写入设备和地址信息；HomePage 通过 Provider 订阅设备列表变化并刷新界面。
[修改]设备发现交互还需要考虑多网卡、重复广播和离线判断。广播发送服务会枚举可用 IPv4 地址，并优先使用计算得到的广播地址发送公告；如果无法得到精确广播地址，则使用 255.255.255.255 作为兜底目标。广播接收服务收到 payload 后不直接修改 UI，而是交给发现控制器校验协议版本、设备 ID、TCP 端口和地址列表。发现控制器会过滤本机设备和短时间内重复的 nonce，然后把对端设备和地址写入本地数据库。TTL 扫描每 3 秒执行一次，如果 12 秒内没有再次收到某地址的广播，则将地址标记为不可达；当设备没有任何可连接地址时，设备列表显示为离线状态。

文本消息发送采用“本地创建、网络发送、远端确认、状态回写”的处理过程。用户在 ChatPage 输入文本并触发发送后，ChatPageController 先通过 MessageRepository 创建 pending 状态的本地消息；随后 DeviceAddressRepository 返回远端可达地址，TransferConnection 建立 TCP 连接，FrameCodec 将消息编码为 textMessage 帧并发送给 RemoteDevice；远端设备返回确认帧后，MessageRepository 将消息状态更新为 sent；如果连接或确认失败，消息状态更新为 failed。
[修改]文本消息采用“先落库、再发送、后确认”的设计。先落库可以保证即使网络发送失败，用户仍然能够在聊天页看到失败消息并进行重试；发送阶段通过可连接地址建立 TCP 连接并发送 textMessage 帧；确认阶段等待对端返回 textMessageAck。如果连接建立失败、确认超时或远端返回错误帧，消息状态会更新为 failed，并记录错误信息。聊天页通过会话 Provider 监听消息表，因此发送状态变化可以自动反映到 UI。

文件传输采用“附件消息创建、文件协商、分片传输、完成确认”的处理过程。用户在 ChatPage 选择文件后，ChatPageController 创建附件消息，FileTransferCoordinator 检查文件大小并选择可达地址；发送端先发送 fileOffer，远端返回 fileOfferAck 后开始按 1MB 分片发送 fileChunk；接收端在写入分片后定期返回 fileChunkAck，TransferProgressStore 持续更新 UI 和通知进度；全部分片发送后，发送端发送 fileComplete，远端完成校验并返回 fileCompleteAck，双方更新附件状态为完成。
[修改]文件传输采用“控制帧 + 数据帧 + 进度状态”的交互模型。控制帧负责协商文件元信息和完成确认，数据帧负责承载二进制分片。发送端在读取文件前校验大小上限，防止超出系统设定的 16GB 范围；读取时按 1MB 分片流式发送，不把完整文件一次性加载到内存。接收端在收到 offer 后创建本地接收文件，优先写入下载目录中的 Hydrop 文件夹，必要时退到应用支持目录。进度以附件 ID 为键写入 TransferProgressStore，UI 和通知服务都从同一份进度快照读取数据，防止页面进度和通知进度不一致。
[修改]异步交互设计遵循“事件进入、状态落点、界面订阅”的路径。用户操作、UDP 广播、TCP 帧、文件 I/O 和系统运行状态事件都属于输入事件；事件进入 Controller 后被转换为数据库更新或 Riverpod 状态更新；界面只订阅这些状态，不主动轮询网络和文件系统。设备页订阅设备列表和最近消息摘要，聊天页订阅会话消息和附件进度，设置页订阅设置项和本机信息。这种方式可以降低页面之间的耦合，也能让同一状态同时服务于手机端单栏界面和桌面端双栏界面。
[修改]对于可能耗时的任务，Hydrop 采用异步 Future 和 Stream 组合。发现广播按周期执行，收到 payload 后异步写入设备和地址；文件传输按分片顺序处理，每个分片发送后更新进度；接收端在数据到达后立即写入文件并报告进度。由于 Flutter UI 线程需要保持流畅，系统防止在页面构建过程中执行文件读取、哈希计算和网络等待。耗时操作由应用层或基础设施层完成，页面只根据 Provider 返回的加载、成功和错误状态决定展示内容。

## 4.4 状态迁移设计

[修改]系统中最重要的状态对象是设备连接状态、消息发送状态和附件传输状态。状态迁移分析用于描述对象运行状态及触发状态变化的事件，适合放在系统设计章节。状态设计的目标是让 UI 能清楚表达“正在处理、已经完成、发生错误、等待用户操作”等状态，同时保证异常发生后能够落库并恢复。

附件传输需要区分数据库状态和运行时进度阶段。数据库中的附件状态包括 pending、transferring、saved 和 failed，用于持久化记录；Riverpod 进度快照中的阶段包括 pending、transferring、paused、completed 和 failed，用于界面实时展示。附件任务从 pending 开始，远端确认 offer 后进入 transferring；用户暂停时，运行时阶段进入 paused，数据库仍保留可恢复所需的附件记录；用户取消、连接失败或校验失败会进入 failed；当全部分片发送、校验和完成确认均成功后，运行时阶段进入 completed，数据库附件状态写为 saved。
消息发送状态包括 pending、sending、sent、failed 和 received。发送端消息从 pending 进入 sending，收到确认后进入 sent，超时或连接异常进入 failed；接收端消息进入 received。设备状态包括 localNetwork 与 disconnected，设备收到广播时进入在线状态，TTL 到期时进入离线状态。
[修改]传输进度状态不仅包含阶段，还包含方向、已传字节、总字节、瞬时速度、更新时间和错误信息。方向用于区分发送端和接收端；字节数用于计算百分比；速度由相邻两次进度快照的字节差和时间差计算；错误信息用于在 UI 中展示失败原因。这种处理使同一个附件卡片既能表达发送中的进度，也能表达接收中的进度，并支持暂停、取消、失败和完成后的状态展示。
[修改]状态迁移设计还区分了可持久化状态和瞬时状态。消息发送状态、附件传输状态、已传字节、文件路径、错误原因等信息需要写入数据库，因为它们直接影响历史记录和重启后的恢复。输入框焦点、设置页选中的分区、设备搜索关键字等信息只影响当前界面，不需要持久化。通过这种划分，数据库不会保存大量临时 UI 状态，应用重启后也能恢复真正影响业务连续性的记录。
[修改]异常状态是状态迁移设计中的重点。文本消息发送失败后保留消息记录并显示失败状态，用户可以根据错误提示决定是否重试或删除；文件传输失败后保留附件记录和错误原因，防止用户误以为文件已经成功发送；设备 TTL 过期后不会删除设备，而是把设备显示为离线，方便用户查看历史会话。长按删除设备记录属于用户主动清理设备列表的操作，与自动离线判断不同，因此需要单独设计入口和确认反馈。

## 4.5 通信协议设计

发现协议基于 UDP 广播。广播目标端口为 39175，payload 类型为 hydrop.discovery.hello，协议版本为 1。payload 包含设备 ID、显示名称、TCP 端口 39176、能力列表、nonce、发送时间和地址列表。nonce 用于短时间内过滤重复广播，地址列表用于记录对端在不同网卡或地址族下的可达信息。
[修改]发现协议采用 UDP 的原因是设备发现强调低成本、低延迟和不用预先建立连接。广播 payload 中的功能列表用于声明设备支持文本、图片、视频、普通文件和测速功能；地址列表用于处理多网卡场景，使对端可以记录不同网卡下的候选 IP 和端口。广播间隔设计为 10 秒，既可以让设备列表及时刷新，又防止过于频繁地占用局域网带宽。设备 TTL 设计为 12 秒，略长于广播间隔，使偶发丢包不会立刻导致设备离线；TTL 扫描间隔为 3 秒，用于较快地将长期不可见设备置为离线。
TCP 通信协议基于 FrameCodec。每个帧由 4 字节 header 长度、4 字节 body 长度、JSON header 和 binary body 组成。header 中包含帧类型、协议版本、消息 ID、附件 ID、文件名、文件大小、偏移量、校验方式等元信息；body 用于承载文本内容或文件分片二进制数据。该设计避免了文本行协议在二进制传输中的边界问题，也使文本消息和文件传输可以使用统一连接语义。
FrameCodec 的 header 使用 JSON 是为了保证协议字段具备可读性和扩展性，body 使用二进制是为了避免文件内容经过文本编码导致体积膨胀。协议为 header 和 body 分别设置最大长度限制，header 最大 16KB，单个 body 最大 1MB，防止异常数据包导致内存占用失控。所有帧都携带协议版本和帧类型，接收端可以根据类型分发到文本、文件、心跳、测速或错误处理逻辑。
文件传输协议由控制帧和数据帧组成。发送端先发送 fileOffer，接收端校验后回复 fileOfferAck，随后发送端按 1MB 分片发送 fileChunk，接收端定期返回 fileChunkAck。文件发送完成后，发送端发送 fileComplete，接收端完成校验与落盘后回复 fileCompleteAck。异常情况下双方可发送 error 帧并更新本地状态。
[修改]文件传输协议还包含可靠性控制。发送端对分片发送设置重试次数，连续失败后将任务置为失败；接收端根据 offset 和 attachmentId 识别当前附件进度，并定期回传 chunk ack。系统限制最大并发传输数为 2，防止多个大文件同时竞争网络和磁盘资源。心跳帧用于判断长时间无数据时连接是否仍然有效，连接异常时 UI 可及时进入 failed 或 paused 状态。对于可恢复传输，系统会保存断点元数据，应用重启后由运行时尝试恢复中断任务。
[修改]协议字段设计采用“必要字段固定、扩展字段可追加”的方式。发现 payload 中固定包含类型、协议版本、设备 ID、显示名称、TCP 端口和功能列表；传输帧 header 固定包含帧类型和协议版本，不同帧再追加各自所需的消息 ID、附件 ID、偏移量、文件名、文件大小或错误原因。接收端先校验协议版本和帧类型，再进入具体处理分支。这样可以在后续增加缩略图、加密参数或更细的传输阶段时，减少对已有帧结构的破坏。
[修改]协议设计还考虑了边界与错误输入。FrameCodec 在解码前先读取 header 长度和 body 长度，并检查它们是否超过上限；header 必须是 JSON 对象，body 长度不能超过单帧上限。对于设备发现，系统会过滤本机设备和重复 nonce，防止同一设备的重复广播不断写入数据库。对于文件传输，系统限制最大文件大小和最大并发数，防止误选超大文件或同时传输过多文件导致内存、磁盘和网络压力失控。

## 4.6 界面与部署设计

[修改]界面风格采用黑白灰、直角、2px 内部分割线和 Material 组件。页面像表格一样只保留内容之间的内边框，去掉外围装饰边框，防止使用大面积背景图。按钮、输入框、列表项和面板均采用直角设计，在线设备使用正常文本颜色，不在线设备使用灰色文本。
一级入口只保留设备页和设置页。移动端使用底部导航，桌面端使用左侧导航。设备页在手机上为单栏列表，点击设备后进入聊天页；桌面端为双栏布局，左侧显示设备列表，右侧显示选中设备的聊天内容。设置页在不同宽度下调整排列方式，桌面端可使用多列布局，移动端使用单列纵向排列。
响应式设计采用窗口等级划分：小于 600 像素为 compact，600 到 839 像素为 medium，840 到 1199 像素为 expanded，1200 像素及以上为 large。compact 与 medium 使用底部导航，expanded 与 large 使用左侧导航。设备页在 expanded 宽度下设备列表宽度为 320 像素，在 large 宽度下为 360 像素；页面边距控制在较小范围，使内容尽量占满可用空间。该设计保证手机端保持单手可用，桌面端则提高信息密度，减少设备列表和聊天内容之间的来回切换。
[修改]聊天界面采用类即时通信软件布局。消息气泡按发送与接收方向左右排列，接收消息使用黑色背景，发送消息使用白色背景，深色主题下保持对应反差。图片消息支持内联预览，文件消息展示文件名、大小、状态、速度和进度。消息操作默认收敛到长按或悬停菜单，减少常态界面的视觉干扰。输入栏为方形，聚焦后边框加重，弹窗统一使用 bottom sheet。
[修改]设置页在设计上承担原本本机信息页的功能，因此设置页不是单纯的偏好配置页，而是系统信息和整体设置的聚合入口。其左侧或上层列表包含本机信息、外观、传输、发现、隐私和关于等分区；桌面端右侧展示所选分区详情，移动端通过 bottom sheet 展示详情内容。所有弹窗统一使用 bottom sheet，可以保持手机端和桌面端交互一致，也防止普通 AlertDialog 在复杂响应式布局中产生尺寸问题。
[修改]界面信息密度按设备类型调整。手机端宽度有限，因此设备页只展示列表，进入聊天后再展示消息内容；桌面端有足够横向空间，设备列表和聊天内容并排显示，减少用户在设备列表和会话之间的来回跳转。设置页也采用同样思路：手机端点击设置项后使用 bottom sheet 展开详情，桌面端直接在右侧展示详情。这样的响应式设计并不是简单放大或缩小控件，而是根据窗口宽度改变信息组织方式。
[修改]交互设计以“少入口、少干扰、状态可见”为原则。一级导航只保留设备和设置两个入口，传输页不作为一级页面出现；聊天消息的复制、删除、保存等操作收敛到长按或悬停菜单，常态下只展示消息内容和传输状态；文件传输中的进度、速度、暂停、取消、完成和失败状态直接显示在附件卡片中，使用户不用进入单独页面就可以判断传输情况。设置类操作统一放入设置页，防止本机信息、二维码、主题和语言入口分散在多个页面。

系统在局域网环境中采用对等部署方式。Device A 与 Device B 是两个同构节点，每个节点内部都包含 Flutter App、SQLite 数据库、下载目录 Hydrop 文件夹、UDP 发现端口 39175 和 TCP 传输端口 39176。两个节点之间通过 UDP 广播链路完成设备发现，通过 TCP Socket 链路完成文本消息和文件传输。操作系统作为外部运行环境，为应用提供文件选择、通知、网络接口和应用生命周期能力。
[修改]部署设计中每台设备都是独立节点，既可以作为发送端，也可以作为接收端。应用不依赖中心服务器，设备发现和数据传输都在局域网内完成。SQLite 数据库存储在本机应用数据目录中，接收到的文件优先保存到下载目录中的 Hydrop 文件夹，下载目录不可用时保存到应用支持目录下的 Hydrop 文件夹。操作系统为应用提供网络接口枚举、文件选择、通知权限和应用前后台运行状态事件。移动端可能受到后台运行限制，因此系统进入后台后不保持连续广播，而是采用低频短窗口维护方式，尽量兼顾能耗与可用性。

## 4.7 数据持久化与一致性设计

[修改]Hydrop 采用本地 SQLite 数据库保存主要业务数据。数据库设计围绕“设备、地址、会话、消息、附件、设置、本机信息、统计”展开。设备表记录对端设备的稳定身份和在线状态；设备地址表记录同一设备在不同网络环境下出现过的 IP、端口和网卡信息；消息表记录文本消息和附件消息的基本信息；附件表记录文件名、本地路径、传输状态、已传字节、校验值和缩略图路径。这样的表结构使设备发现、聊天记录和文件传输能够在同一个本地数据模型中关联起来。
[修改]数据一致性主要通过稳定业务 ID 和唯一约束完成。设备使用 deviceId 识别，地址使用设备 ID、IP 和端口组合识别，消息使用本地消息 ID 识别，附件使用 attachmentId 识别。设备发现可能在短时间内收到多次相同广播，文本消息可能因重试产生重复确认，文件传输也可能在失败恢复时重复写入进度；这些场景都需要数据库层的唯一约束和仓库层的 upsert 操作共同处理。这样可以减少重复记录，也能让 UI 始终订阅同一条业务记录。
[修改]数据库状态和 Riverpod 状态在设计中有明确分工。数据库保存重启后还要恢复的数据，Riverpod 保存界面正在观察的数据。设备列表、消息时间线和设置项可以直接由数据库 Stream 驱动；传输进度刷新频率较高，如果每次变化都立即写入数据库，会增加磁盘压力。因此 Hydrop 使用进度存储向 UI 高频推送，同时按时间间隔和字节阈值把关键进度写入数据库。传输完成、失败、暂停等最终状态不受节流影响，需要及时落库，保证界面和历史记录一致。
设备地址表在本系统中承担了比普通通讯录地址更复杂的职责。同一台远端设备可能同时出现在 Wi-Fi、热点、虚拟网卡或桌面端多网卡环境中，因此不能只在设备表中保存一个 IP 地址。系统将设备身份和地址信息拆开：device_items 只保存远端设备的稳定身份、显示名称和连接状态，device_address_items 保存 IP、端口、网卡名称、网络签名、广播地址、可达性、延迟和速度等信息。这样做的好处是设备名称变化不会破坏地址历史，地址变化也不会影响聊天记录与设备身份的关联。
消息表和附件表的拆分也是为了适应聊天式传输界面。一条文本消息只需要保存文本内容、方向、发送状态和错误信息；一条文件消息还需要保存文件名、路径、MIME 类型、总字节、已传字节、校验值和传输状态。如果把这些字段全部放在消息表中，文本消息会携带大量空字段，后续扩展图片缩略图、视频预览或文件保存状态时也会使消息表越来越臃肿。因此系统把共同的会话信息放在 message_items 中，把附件相关字段放在 message_attachment_items 中，通过 message_id 建立关联。聊天页读取消息时间线时，可以先得到消息主体，再按消息 ID 关联附件数据。
设置表和本机资料表没有合并，原因在于二者的变化频率和业务含义不同。设置表保存主题、语言、传输加密开关和自动恢复传输开关，属于用户偏好；本机资料表保存本机显示名称和本机设备 ID，属于设备身份。主题和语言变化主要影响本机界面，本机显示名称变化则会进入发现广播 payload，影响对端设备页看到的名称。将它们拆开后，设置页仍然可以把两类信息放在同一界面展示，但数据层不会把偏好配置和设备身份混在同一张表里。
一致性设计还需要处理“删除”的语义。用户在设备页长按删除设备时，目标是从设备列表中去掉该设备显示记录，而不是简单清空某个聊天会话；用户在聊天页删除文件或图片消息时，目标是删除消息记录，默认不删除本地文件。二者的行为边界必须明确，否则容易出现用户误删已接收文件或设备列表无法清理的问题。因此系统把设备记录删除、会话消息删除和本地文件删除设计成不同动作，并在页面交互上分别放在设备长按菜单和消息操作菜单中。
数据库版本设计采用 schemaVersion = 1。由于本系统处于第一版开发阶段，开发过程中可以通过清理本机应用数据重新创建数据库，因此不保留历史迁移脚本。论文中也不描述多版本迁移过程，避免与代码行为不一致。首次创建数据库时由 Drift 创建全部表，并建立必要的自定义唯一索引；如果后续进入发布阶段，再根据版本演进补充 MigrationStrategy。该处理符合快速开发阶段的实际情况，也减少了毕业设计说明中“文档写了迁移、代码却没有迁移”的偏差。
统计表 point_items 不是核心传输链路的一部分，但它为后续使用情况分析留下了位置。系统可以记录首次启动时间、发现设备数量、聊天过的设备数量、已发送文本字符数和文件字节数。这些数据不会影响设备发现和文件传输是否成功，因此不应与消息表或附件表强耦合。把统计信息单独存储，可以避免统计更新影响会话数据，也便于后续在设置页或关于页中展示简要使用情况。

## 4.8 可维护性与扩展性设计

[修改]系统后续可能继续增加端到端加密、缩略图生成、传输队列、历史文件清理、复杂网络发现方式和更完整的性能测试。为方便扩展，设计中尽量把变化点集中在明确模块内。协议字段扩展集中在 payload 和 FrameCodec header 中；传输策略扩展集中在 FileTransferCoordinator；发现方式扩展集中在发现控制器和发现服务；设置项扩展集中在设置仓库和设置页；UI 样式扩展集中在通用组件和响应式工具类中。
[修改]可维护性设计还体现在错误处理和日志边界上。网络和文件传输错误由应用层捕获后转换为业务状态，页面不直接处理底层异常栈；通知、toast 和应用内提示只是反馈渠道，不决定传输主流程是否成功；数据库异常需要在仓库层处理，防止异常穿透到页面构建过程。每个模块只处理自己能理解的错误，用户可见状态稳定地呈现在设备页、聊天页和设置页中。
[修改]从代码组织上看，系统尽量不让页面文件承担过多业务逻辑。设备页只关心设备列表和当前选中的设备，聊天页只关心某个对端设备的会话，设置页只关心本机信息和偏好设置。文本发送、文件选择后的消息创建、传输进度更新、设备删除和设置保存，都通过 Controller 或 Provider 暴露的方法完成。修改 UI 风格时不用重写发现协议和传输协议，调整传输策略时也不用重新设计页面结构。
扩展性还体现在协议字段的可追加性。发现 payload 已经包含 type、version、deviceId、displayName、tcpPort、capabilities、nonce、sentAt 和 addresses 等字段，后续增加设备平台、应用版本或加密能力时，可以继续追加字段而不破坏基本发现能力。FrameCodec header 也采用 JSON 对象，文本消息、文件 offer、分片、完成确认、心跳和错误帧都可以在统一结构下扩展字段。只要接收端先校验协议版本和帧类型，再按字段是否存在进行兼容处理，协议演进的成本就比较可控。
[修改]传输模块的可维护性重点在于把“任务控制”和“字节传输”分开。用户看到的是附件消息的暂停、取消、失败、完成和速度；底层实际执行的是文件读取、Socket 写入、分片确认和状态回写。FileTransferCoordinator 把这两部分连接起来，但页面不直接接触 Socket，数据库也不直接管理 Socket 运行状态。后续若要增加传输队列、并发优先级、断点续传或加密流包装，应优先在传输协调器和连接服务中处理，而不是把逻辑分散到聊天页。
[修改]设置模块扩展时也要保持边界清楚。主题和语言由 MainApp 读取，传输加密和自动恢复由运行时或传输模块读取，本机显示名称会写入发现广播 payload。设置页只是这些配置的编辑入口，不应把设置值写死在页面内部。通过设置仓库和 Provider 暴露设置状态后，用户切换语言时界面可以刷新，修改显示名称后后续广播会带上新名称，切换自动恢复后也会影响启动恢复逻辑。
[修改]系统的错误信息需要同时照顾开发者和普通用户。开发者需要在日志中看到对端设备 ID、本地消息 ID、附件 ID、文件名和错误类型等定位信息；普通用户只需要知道“发送失败”“文件过大”“连接中断”“对端不可达”等结果。因此应用层记录详细日志，页面层展示简洁状态，避免用户界面被技术细节占满，也保留开发调试需要的线索。
[修改]可维护性还要求文档、论文和代码保持一致。本论文只把设备页和设置页作为一级入口，不再描述独立传输页或我的页；只描述 schemaVersion = 1 和首次创建数据库，不再描述多版本迁移；只描述当前文件传输协议参数，不写未经实测的吞吐量结论。这能减少论文和程序行为之间的矛盾，也方便后续按真实代码继续维护毕业设计材料。

# 5 系统实现

[修改]本章说明系统从设计到代码的落地方式。根据论文结构要求，本章不直接放置代码清单，只描述关键实现思路、模块职责和运行机制；关键代码统一整理到附录 C。

## 5.1 启动与运行时实现

应用启动流程为 main.dart -> ProviderScope -> MainApp -> appRuntimeProvider。入口创建 Riverpod 容器，并注入 Talker 的 Riverpod 观察器。MainApp 负责应用级主题、语言、路由和生命周期处理：应用恢复到前台时调用运行时恢复网络能力，应用进入非前台状态时暂停发现服务和传输服务，并保留短窗口后台维护能力。
运行时对象 AppRuntime 负责协调通知权限、发现服务、传输服务和中断传输恢复。它在创建时请求通知权限并尝试恢复中断传输；在前台恢复时启动 DiscoveryController 和 TransferServerController；在后台或暂停状态下停止实时发现和 TCP 服务，降低资源占用并避免连接状态混乱。
启动流程没有在 main 函数中直接创建数据库、Socket 或页面控制器，而是通过 ProviderScope 建立依赖容器。这样做可以让数据库、仓库、控制器、通知服务和传输服务都由 Riverpod 管理生命周期。页面首次读取某个 Provider 时，对应对象才会被创建；应用退出或 Provider 被释放时，相关资源可以通过 ref.onDispose 清理。对于需要全局存在的运行时对象，MainApp 会读取 appRuntimeProvider，使发现服务、TCP 服务和中断恢复能力在应用层被统一拉起。
应用生命周期处理是运行时实现中的重点。移动端用户可能频繁切换应用，桌面端用户也可能最小化窗口或改变窗口焦点。如果设备发现和 TCP 服务完全依赖某个页面存在，就会出现进入设置页后发现停止、返回设备页后重复启动监听等问题。因此 AppRuntime 作为独立运行时对象存在，不属于某个页面。它根据前台、后台和暂停等状态决定是否启动发现广播、UDP 监听和 TCP 服务，并在资源释放时关闭对应 Stream、Timer 和 Socket。
[修改]通知权限也放在运行时处理，而不是放在文件发送按钮中处理。传输通知是系统级反馈功能，适合在应用启动阶段提前申请或检查；真正发送文件时，只需要调用通知服务更新进度。如果通知插件缺失、权限不足或平台不支持，运行时会把错误控制在通知模块内，不让异常影响文件传输主流程。这个处理方式在桌面端尤其重要，因为 macOS 通知权限和插件注册状态可能与移动端不同。
[修改]中断传输恢复由 AppRuntime 触发，说明它属于应用级行为，而不是某个页面自己的逻辑。系统启动后会检查数据库中处于 transferring、pending 或 paused 等未完成状态的附件记录，再根据自动恢复设置决定是否尝试恢复。恢复过程仍然交给 FileTransferCoordinator 处理，而不是由页面扫描数据库后自行恢复。这样即使用户先打开设置页，或者设备页还没有选中聊天对象，未完成的传输任务也能由运行时处理。

## 5.2 路由与响应式主界面实现

系统路由只包含两个一级页面和一个会话页面。AppRoute 作为应用主壳，内部挂载 HomeRoute 与 SettingsRoute；ChatRoute 独立存在，用于从设备页进入指定设备的聊天页面。ChatRoute 携带远端设备 ID 和显示名称，保证聊天页可以明确绑定设备上下文。
[修改]主界面根据窗口宽度决定导航形式。桌面端使用左侧导航栏，导航项只保留设备页和设置页；移动端使用底部导航栏。设备页在桌面端可以和聊天区组成双栏，在移动端则先显示单栏设备列表，点击设备后再通过路由进入聊天页。这样的实现减少了页面入口数量，也符合当前程序只保留两个一级 tab 的产品形态。
[修改]路由结构刻意保持较少层级。设备页和设置页是用户进入应用后最常用的两个入口，因此放入 AppRoute 的子路由中；聊天页虽然是主要功能页面，但它必须依赖对端设备上下文，不能作为没有参数的一级 tab 出现。ChatRoute 要求 remoteDeviceId 和 displayName 两个参数，前者用于查询消息、附件和传输进度，后者用于标题展示和空状态提示。通过参数强制约束，可以防止进入聊天页却不知道对应设备的情况。
[修改]响应式主界面通过窗口等级统一处理，而不是在每个页面中零散判断屏幕宽度。compact 和 medium 宽度使用底部导航，符合手机端用户手指操作习惯；expanded 和 large 使用左侧导航，给内容区域留下更多垂直空间。设备页在桌面端内部再拆成设备列表和聊天内容两列，其中设备列表宽度固定在适合扫描的范围内，聊天内容占据剩余区域。这样设备页在桌面端接近即时通信软件的布局，在移动端仍保持清晰的页面栈。
[修改]导航项被压缩为设备和设置两个，也减少了状态同步成本。独立传输页虽然可以集中展示任务，但会让文件传输从聊天上下文中抽离出来；我的页如果独立存在，也会让本机名称、二维码和偏好设置分散。当前实现把传输状态放回附件消息，把本机信息合并到设置页，使用户在两个入口之间就可以完成主要操作。这与系统面向局域网设备直传的定位更一致。
[修改]主界面在视觉上使用黑白灰、直角和内部分割线。页面外缘不再使用明显外框，也不使用每日壁纸或玻璃背景，防止内容被装饰元素干扰。桌面侧边导航、手机底部导航、设备列表和聊天区域之间主要依靠 2px 分割线建立结构关系。这样的风格更接近工具型应用，适合文件传输这种需要关注状态和效率的场景。

## 5.3 设备发现实现

[修改]设备发现由发现控制器、广播发送服务、广播接收服务、设备仓库和地址仓库协作完成。发现控制器启动后，广播服务周期性发送本机公告，公告内容包含 payload 类型、协议版本、设备 ID、显示名称、TCP 端口、功能列表、nonce、发送时间和地址列表。接收服务监听 UDP 39175 端口，解析收到的公告并传递给发现控制器。
[修改]设备发现发送的是 JSON 格式的广播，类型固定为 hydrop.discovery.hello，协议版本为 1。广播里会写入本机设备 ID、显示名称、TCP 端口 39176、支持的功能、随机 nonce、发送时间和本机地址列表。支持的功能主要包括文本、图片、视频、普通文件传输和测速。发现控制器启动后会先发一次广播，之后每隔 10 秒再发一次，这样同一局域网里的其他设备就能在设备页中看到本机。
[修改]发现控制器收到 payload 后，先过滤本机设备和重复 nonce，再将设备信息写入设备表，将地址信息写入设备地址表，并根据可连接地址触发测速调度。TTL 扫描定时检查设备地址的最后可见时间，当超过 12 秒没有刷新时，将对应设备置为离线状态。设备页通过 Provider 订阅设备列表，因此数据库或状态更新后可以自动刷新 UI。
[修改]接收端会在 UDP 39175 端口等待其他设备的广播。收到数据后，系统先把 JSON 内容解析出来，再检查类型、协议版本、设备 ID、显示名称、TCP 端口和地址列表。如果内容不完整，或者协议版本不对，就不会写入设备数据；如果设备 ID 和本机一样，说明收到了自己的广播，也会直接过滤；如果同一设备在短时间内带着相同 nonce 重复出现，系统也会忽略它，防止同一次广播被反复处理。
[修改]广播内容检查通过后，发现控制器会把对端设备写入 device_items 表，把可以连接的地址写入 device_address_items 表。地址记录会保存 IP、端口、网卡名称、网络签名、广播地址、最近发现时间和是否可达等信息。如果广播里没有完整的地址列表，系统会使用 UDP 数据包的来源 IP 作为候选地址，保证后续 TCP 连接至少还有一个可以尝试的目标。
广播发送服务会枚举本机可用 IPv4 地址，并根据地址和子网信息计算广播地址。能够得到准确广播地址时，系统优先向该广播地址发送公告；无法得到准确广播地址时，使用 255.255.255.255 作为兜底目标。这样可以适配普通家庭路由器、手机热点和部分桌面端多网卡环境。公告中携带 addresses 列表，是为了让接收端不仅知道“有一台设备存在”，还知道可以尝试连接哪些 IP 和端口。
广播接收服务只负责 Socket 层监听和 payload 解析，不直接修改设备列表。收到数据后，它把解析结果交给 DiscoveryController。控制器先检查 type 是否为 hydrop.discovery.hello，再检查协议版本、设备 ID、TCP 端口、nonce 和地址列表。若 payload 来自本机设备，则直接丢弃；若 nonce 在短时间内已经处理过，则视为重复广播；若字段不完整，则不写入数据库。这样的分层使 UDP 接收逻辑保持简单，协议校验和业务去重集中在控制器中。
[修改]设备离线不是通过一次连接失败马上判断，而是通过 TTL 超时判断。UDP 广播本身可能丢包，如果一次没有收到广播就把设备置为离线，设备列表会频繁变化。系统设置 10 秒广播间隔和 12 秒 TTL，使一次偶发丢包不会立刻影响界面；TTL 扫描每 3 秒执行一次，如果某个地址长时间没有刷新，就把它标记为不可达。设备是否离线，取决于它是否还存在可达地址，而不是只看最后一次广播时间。
设备发现还与测速和排序有关。设备页展示速度摘要和最后一次传输时间，用户可以据此判断哪台设备更适合接收大文件。测速结果保存到地址或设备相关字段中，既可用于列表展示，也可用于发送文件时选择可达地址。对于同一设备的多个地址，系统可以优先选择最近成功、延迟较低或速度较好的地址。这样设备发现不仅是“看到设备”，还为后续传输建立了地址选择基础。
[修改]设备被发现后，系统还会对候选地址做一次轻量级 TCP 探测。探测结果会记录延迟、平均传输速度和最近一次成功连接时间，并保存到设备地址或设备信息中。设备页会优先显示在线设备，同时显示速度摘要和最后一次传输时间。用户不用查看 IP 和端口，也能大致判断哪台设备更适合接收大文件。
[修改]发现服务会跟随应用状态变化。应用在前台时，系统会持续发送广播并监听 UDP 端口；应用进入后台或暂停后，会停止持续发现，只保留少量必要的维护动作，减少手机耗电和电脑资源占用。应用回到前台后，AppRuntime 会重新启动 DiscoveryController，设备列表也会继续刷新。
二维码连接是设备发现的补充手段。自动发现依赖局域网广播，如果路由器限制广播、设备处于复杂网络或权限不完整，二维码可以把必要连接信息直接交给对端。设置页中展示二维码连接入口，设备页空状态也可以引导用户通过扫码连接。二维码内容经过精简，只保留连接所需的核心信息，避免 payload 过大导致扫描困难。

## 5.4 消息与文件传输实现

文本消息和文件传输均基于 TCP 39176 端口和 FrameCodec 帧协议实现。FrameCodec 使用 4 字节 header 长度、4 字节 body 长度、JSON header 和 binary body 组织数据帧。文本消息使用 textMessage 和确认帧完成发送状态闭环；文件传输使用 fileOffer、fileOfferAck、fileChunk、fileChunkAck、fileComplete 和 fileCompleteAck 完成传输闭环。
[修改]文件发送由文件传输协调器负责。发送端先创建附件消息并检查文件大小，随后选择可连接地址并建立 TCP 连接。文件内容按 1MB 分片读取和发送，不把完整文件一次性加载到内存。接收端收到文件 offer 后创建接收记录，优先按分片写入下载目录中的 Hydrop 文件夹，下载目录不可用时写入应用支持目录，并在完成后进行校验和状态更新。传输过程中若发生连接中断、确认超时、用户暂停或用户取消，系统会关闭对应连接并更新附件记录和运行时进度。
[修改]文本消息发送从 ChatPageController 发起。用户输入文本后，控制器先创建本地消息记录，使消息立即显示在时间线中；随后根据对端设备 ID 查询可连接地址，通过 TCP 连接发送 textMessage 帧；接收端处理文本后返回确认帧。发送端收到确认后把消息状态改为 sent，如果超时或收到错误帧，则把状态改为 failed 并保存错误原因。这个流程保证了消息不会因为网络失败而无声消失。
文件传输和文本消息共用 FrameCodec，但二者的业务粒度不同。文本消息通常体积较小，可以一次性放入帧 body；文件传输必须拆成多个 fileChunk 帧，并通过 attachmentId、offset 和 totalBytes 关联传输过程。发送端发送 fileOffer 时，先把文件名、大小、MIME 类型、附件 ID 等元信息交给接收端；接收端确认后再开始接收分片。这样接收端可以在真正写入文件前检查是否能够接收，并创建对应的消息和附件记录。
[修改]大文件传输实现防止一次性读入内存。发送端通过文件流按 1MB 读取分片，每次读取后立即编码为帧并写入 Socket；接收端收到分片后按 offset 写入目标文件，并更新 transferredBytes。SHA-256 校验也应采用流式思路处理，防止在几 GB 文件场景中把完整文件加载到内存。这样的实现虽然代码比一次性读写复杂，但更符合大文件传输需求，也能降低移动设备内存压力。
[修改]暂停和取消属于用户控制功能。暂停传输时，系统需要停止继续发送或接收数据，关闭相关连接，并把运行时进度阶段更新为 paused，同时保留数据库中的附件记录以便后续恢复；取消传输时，系统将任务置为 failed 或取消结果，并更新 UI 与通知。暂停并不等同于删除消息，用户仍然可以在聊天记录中看到附件和进度；删除消息也不等同于删除本地文件，接收文件优先保存在下载目录的 Hydrop 文件夹中，用户可在系统文件管理器中继续访问。
[修改]接收端保存路径优先使用下载目录下的 Hydrop 文件夹；如果平台无法返回下载目录，则退到应用支持目录下的 Hydrop 文件夹。这样用户在常见平台上接收文件后不需要进入应用私有目录查找，也方便在桌面端或手机文件管理器中直接打开。保存时需要处理文件名冲突，防止同名文件覆盖。系统通过排他创建文件并追加序号或时间戳的方式保证每次接收都有独立路径，再把最终路径写入附件记录。
[修改]错误处理贯穿整个传输链路。地址不可达、连接建立失败、fileOfferAck 超时、分片发送失败、完成确认失败、文件超过大小限制、磁盘写入失败和校验失败都需要转换成附件状态和错误信息。页面不展示底层异常栈，而是在附件卡片上显示失败状态；日志保留更详细的中文错误，方便开发阶段定位问题。用户可以理解结果，开发者也能追踪原因。

## 5.5 传输进度与通知实现

[修改]传输进度由 Riverpod 统一管理。系统以附件 ID 为键保存传输进度快照，快照内容包括传输方向、阶段、已传字节、总字节、速度、更新时间和错误信息。聊天页中的附件卡片按附件 ID 订阅进度，因此只需要刷新相关附件的 UI。
[修改]通知服务用于在系统通知中显示传输进度。移动端使用临时 toast 显示轻量提示，桌面端使用应用内提示组件。通知功能属于辅助反馈，如果通知插件初始化失败，系统不会中断文件传输主链路，而是记录错误并继续执行传输。
传输进度没有直接由聊天页 setState 维护，而是由 TransferProgressStore 统一保存。每个附件的进度快照都以 attachmentId 为键，包含 direction、phase、transferredBytes、totalBytes、bytesPerSecond、updatedAt 和 errorMessage。聊天页中的附件卡片使用 transferProgressProvider(attachmentId) 精确订阅，这样一个文件的进度变化不会迫使整条消息列表全部重建。
[修改]速度计算依赖连续两次进度快照之间的字节差和时间差。发送端和接收端都通过同一进度模型暴露速度，因此 UI 可以用同一套组件展示上传和下载状态。对于小文件，进度可能很快从 0 进入完成；对于大文件，进度会持续更新。进度条不应简单显示满格，而应根据 transferredBytes 和 totalBytes 计算百分比；如果 totalBytes 不合法或未知，应显示明确的等待或异常状态，防止给用户造成“已经完成”的误解。
[修改]进度持久化需要节流。传输中的每个 1MB 分片都可能产生进度事件，如果每次事件都立即写数据库，长时间大文件传输会造成大量写入。Hydrop 通过 Riverpod 进度存储向 UI 高频推送，再按阈值把关键进度写回数据库。完成、失败、暂停和取消属于关键状态，必须及时落库；普通传输进度则可以按字节差或时间间隔写入，以兼顾 UI 流畅度和 SQLite 写入压力。
[修改]通知服务和聊天页读取同一份进度数据，防止“通知进度”和“聊天页进度”各自计算。移动端在传输开始、失败或完成时可以通过 fluttertoast 给出短提示，传输过程中则通过系统通知展示进度；桌面端用户通常直接看着窗口操作，因此更适合使用应用内提示。通知初始化失败不应影响文件发送，因为通知只是反馈渠道，不是传输协议的一部分。
[修改]进度状态还为恢复和诊断提供依据。附件记录中的 transferredBytes、transferStatus 和 errorMessage 可以在应用重启后帮助判断哪些任务未完成；运行时恢复时可以根据这些字段决定是否继续尝试。即使恢复功能后续进一步完善，当前进度模型也已经把方向、阶段、字节数和错误原因拆开，为后续扩展保留了清晰入口。

## 5.6 设备页、聊天页与设置页实现

设备页使用设备相关 Provider 渲染列表。每个设备项展示名称、速度、最后一次传输和在线状态。不在线设备文本置灰。长按设备项会打开底部菜单，提供删除设备显示记录的操作；该操作删除设备列表中的记录，而不是仅清空聊天消息。
[修改]聊天页从设备上下文进入，页面根据对端设备 ID 读取消息时间线。文本消息以聊天气泡展示；图片消息支持内联预览；视频和普通文件以附件卡片展示，卡片中包含文件名、大小、状态、进度和速度。消息删除只删除消息记录，默认不删除本地文件。
[修改]设置页是当前一级入口之一，并整合本机信息功能。它展示和维护本机显示名称、设备 ID、二维码连接、本地 IP、诊断信息、主题、语言、传输加密开关和自动恢复传输开关。本机显示名称支持直接在页面上修改，不再通过独立弹窗完成。
[修改]设备页的主要内容是设备列表。列表项不显示过多网络字段，而是优先展示用户最关心的信息，包括设备名称、在线状态、速度摘要和最后一次传输时间。不在线设备使用灰色文本，在线设备使用正常文本颜色。长按菜单采用 bottom sheet，使移动端和桌面端保持相同的弹出方式。删除设备操作只针对设备列表中的显示记录，删除后设备页不再展示该设备；如果对端设备再次广播，系统仍会按发现流程重新写入设备。
[修改]桌面端设备页内部采用左设备列表、右聊天内容的结构。当用户选择设备后，右侧直接显示 ChatPage 对应内容；没有选中设备时，右侧显示空状态。移动端不强行在窄屏上塞入双栏，而是点击设备后通过 ChatRoute 进入聊天页。这样的实现防止了手机端内容拥挤，也让桌面端用户可以一边查看设备列表，一边处理当前会话。
[修改]聊天页的消息时间线按会话设备过滤。文本消息使用左右气泡区分发送和接收；接收消息背景为黑色，发送消息背景为白色，深色主题下也保持可辨识的反差。图片消息采用内联预览，用户不需要只看文件名；普通文件和视频以附件卡片呈现，卡片中展示文件名、大小、进度、速度和状态。消息的复制、删除、保存等操作收敛到长按或悬停菜单，常态界面只保留内容和必要状态。
[修改]聊天输入栏采用方形控件。输入框获得焦点后边框加重，发送按钮根据输入内容状态变化，附件按钮负责触发文件选择。手机端键盘弹起时，页面需要根据 MediaQuery 的 viewInsets 调整底部区域，防止输入栏被键盘遮挡或出现负 padding。所有与消息相关的 bottom sheet 都使用响应式约束，防止 AlertDialog 在桌面和移动端之间出现尺寸计算问题。
[修改]设置页把“我的”功能合并进来。本机显示名称可以直接在页面上编辑，减少一个弹窗层级；设备 ID、二维码连接、本地 IP 和诊断信息用于连接和排错；主题、语言、传输加密和自动恢复属于整体设置。桌面端设置页可以使用分区列表加详情区域，移动端则以单列列表和 bottom sheet 展开详情。用户不会再看到单独的 Mine 一级入口，论文和程序都应按设置页整合后的形态描述。
多语言实现覆盖简体中文、繁体中文、英文和跟随系统。界面文本通过 intl 生成的本地化类读取，而不是在页面中硬编码中文字符串。设置页切换语言后，MainApp 从设置 Provider 中读取语言配置并更新 Locale。跟随系统模式下，应用使用系统语言；用户手动选择语言后，界面以用户选择为准。这样可以满足跨平台应用在不同地区设备上的基本语言适配需求。

## 5.7 数据库存储与消息/会话持久化实现

[修改]数据库由 AppDataBase 统一管理。当前版本数据库版本号为 1，首次创建时生成全部表并创建自定义唯一索引；打开数据库前启用 SQLite 外键约束。系统处于第一版开发阶段，因此不保留升级迁移逻辑。
[修改]设备表保存对端设备显示名称、设备 ID、连接状态、平均传输速度和最近传输时间；设备地址表保存设备 IP、端口、网卡、网络签名、可达状态和最后可见时间；连接会话表保存 TCP 会话状态、协议版本、心跳和断开信息；设置表保存主题、语言、传输加密和自动恢复传输偏好；本机信息表保存本机显示名称和本机设备 ID；消息表与附件表保存聊天内容和文件传输状态；统计表保存首次启动、发现设备数和发送统计。
[修改]自定义唯一索引用于约束设备地址、消息本地 ID 和附件 ID，防止重复广播或重试写入造成数据冲突。消息表记录文本、方向、类型、发送状态、本地消息 ID、远端消息 ID 和错误信息。附件表记录文件路径、保存状态、下载进度、附件 ID、文件名、MIME 类型、总字节、已传字节、校验值、缩略图路径和传输状态。
[修改]Drift 的优势在于类型安全和响应式查询。设备页可以订阅设备仓库暴露的设备列表 Stream，聊天页可以订阅指定 remoteDeviceId 的消息 Stream，设置页可以订阅设置表和本机信息表。数据库变化后，Provider 将变化推送到页面，页面不用手动刷新。这种方式特别适合设备发现和消息接收，因为它们可能来自后台网络事件，而不是用户当前页面点击。
消息发送采用先落库策略。创建消息记录后，即使 TCP 发送失败，聊天页仍然能展示该消息并标记失败；如果发送成功，Repository 更新 sendStatus 和远端消息 ID。接收文本消息时，TransferServerController 会把消息写入 message_items，并把方向设置为 received。这样发送端和接收端都使用同一张消息表保存会话历史，页面渲染逻辑也更统一。
[修改]附件持久化需要同时服务发送端和接收端。发送端附件记录保存原始文件路径、文件名、总字节、已传字节和发送状态；接收端附件记录保存最终目标文件路径、接收进度和保存状态，该路径通常位于下载目录 Hydrop 文件夹中，也可能在应用支持目录兜底位置。无论方向如何，附件卡片都通过 attachmentId 关联传输进度，通过 messageId 关联消息气泡。UI 不需要区分“这是发送附件表”还是“这是接收附件表”，只需根据方向和状态调整展示文本。
[修改]唯一索引对局域网广播场景很重要。自动发现会持续收到广播，同一设备同一地址可能在几分钟内写入多次；如果没有唯一约束，设备地址表会产生大量重复记录。系统使用设备 ID、IP 地址和端口作为地址唯一条件，并在仓库层使用 upsert 思路更新 lastSeenAt、isReachable 和速度信息，既保留地址历史，又避免重复广播造成列表膨胀。
[修改]外键约束在数据库打开前启用。消息附件依赖消息，设备地址依赖设备，连接会话可能关联设备地址。启用外键约束可以减少孤立记录，但实际业务中仍需注意删除语义。例如删除设备显示记录时，需要考虑是否同时处理关联地址和会话；删除消息记录时，需要处理附件记录，但默认不删除文件系统中的真实文件。这些策略不应只依赖数据库级联，而应由 Repository 根据业务意图明确执行。

# 6 系统测试与结果分析

## 6.1 功能测试

[修改]功能测试围绕设备发现、文本通信、文件收发、暂停取消、设置切换和本机信息展示等关键流程展开。测试环境为同一局域网内的移动端设备和桌面端设备，测试方法为手动操作并观察应用界面、数据库记录和日志输出是否符合预期。
[修改]设备发现测试主要启动两台设备上的应用，验证双方是否能在设备页看到对方。测试关注设备名称、在线状态、地址记录、速度摘要和最后一次传输时间是否正确展示；关闭其中一台设备后，另一台设备应能在 TTL 失效后将其标记为离线。
文本通信测试：在设备页选择远端设备进入聊天页，发送多条文本消息，验证本地消息是否先以待发送状态展示，发送成功后是否更新为已发送；接收端是否能显示收到的文本消息；发送失败时是否展示失败状态和错误信息。
文件传输测试：分别选择图片、视频和普通文件发送给远端设备，验证发送端和接收端的附件消息、进度、速度、暂停、取消、失败反馈和完成状态是否正确。接收端文件应优先保存到下载目录下的 Hydrop 文件夹中；如果平台不能提供下载目录，则应保存到应用支持目录下的 Hydrop 文件夹中。
[修改]设置测试主要在设置页切换浅色、深色和跟随系统模式，切换系统语言、英文、简体中文和繁体中文，修改本机显示名称，验证界面是否即时更新并在重启后恢复。二维码连接、本地 IP、诊断信息和传输偏好开关也应保持可用。
[修改]设备发现测试还需要覆盖多网卡和重复广播场景。在桌面端同时存在 Wi-Fi、虚拟网卡或热点网络时，系统应能从可用 IPv4 地址中构造地址列表，并将远端地址写入 device_address_items。重复广播不会在设备地址表中产生大量重复记录，lastSeenAt 和可达状态应随广播刷新。若路由器限制广播，可通过二维码连接入口验证基本连接信息是否能够补充自动发现功能。
[修改]聊天页面测试需要覆盖移动端和桌面端两种布局。在移动端，点击设备后应进入单独聊天页，底部输入栏在键盘拉起时不应被遮挡；在桌面端，设备列表和聊天内容应并排显示，选择不同设备时右侧会话内容随 remoteDeviceId 切换。长按消息或附件时，操作入口应通过 bottom sheet 或悬停菜单出现，常态界面不应长期显示复制、删除等按钮。
文件传输测试除了验证成功路径，还应验证异常路径。选择超过 16GB 的文件时，系统应拒绝发送并显示友好错误；传输过程中关闭对端应用或断开网络时，发送端和接收端都应进入失败或暂停状态，而不是一直显示加载；用户点击暂停后，附件卡片应停止继续增加进度；用户删除文件消息时，只删除消息和附件记录，默认不删除已经保存到文件系统中的真实文件。
[修改]设置测试需要关注设置项与其他模块之间的联动。修改本机显示名称后，对端设备页后续收到广播时应显示新的名称；切换主题后，设备页、聊天页、设置页和 bottom sheet 的背景、文本、边框颜色都应同步变化；切换语言后，导航项、设置项、聊天输入提示和错误提示应随语言配置更新。自动恢复传输开关需要在应用启动恢复逻辑中生效，传输加密开关则作为配置项持久化保存。

## 6.2 工程测试

工程测试从代码质量、路由结构、数据库结构和 Provider 依赖四个维度进行。
[修改]静态分析主要通过 Flutter/Dart 静态分析检查类型错误、无效引用和明显代码问题，确保路由参数、Provider 类型、数据库表字段和平台插件调用在编译阶段保持一致。
路由验证：检查路由表中一级页面只包含 HomeRoute 和 SettingsRoute，并确认 ChatRoute 需要远端设备 ID 和显示名称作为上下文。该验证确保设备页、设置页和聊天页的页面层级与产品设计一致。
数据库验证：创建全新数据库后，检查 schemaVersion = 1，确认 8 张表和自定义唯一索引创建成功。因为系统处于第一版开发阶段，不进行升级迁移测试。
Provider 验证：检查设备发现、设置、聊天会话和传输进度 Provider 的依赖关系，确认底层状态变化后 UI 能自动刷新，且传输进度可通过 transferProgressProvider 按附件 ID 单独订阅。
[修改]工程测试不应只看界面能否打开，还需要检查模块边界是否被破坏。例如页面层不应直接创建 RawDatagramSocket 或 ServerSocket，聊天页不应直接写 Drift 表，设置页不应绕过设置仓库直接修改数据库。若这些边界被破坏，短期内功能可能仍能运行，但后续修改协议、数据库或 UI 时会变得困难。因此工程测试需要结合代码审查，确认 Controller、Repository、Service 和页面之间的依赖方向仍然清晰。
[修改]数据库验证还需要关注唯一约束。设备地址表应能处理相同 deviceId、ipAddress 和 port 的重复写入，消息表应防止相同 localMessageId 重复插入，附件表应防止相同 attachmentId 重复插入。此前开发过程中出现过重复列和唯一约束相关问题，这说明数据库设计与写入策略必须配合验证。由于系统不保留迁移逻辑，测试时应使用全新数据库进行创建验证，防止历史开发数据干扰结论。
Provider 验证需要关注重建范围。设备列表更新不应导致整个应用频繁重建，单个附件进度变化不应导致所有消息气泡都重绘。transferProgressProvider 采用 family 形式，可以按 attachmentId 订阅单个任务，这是工程测试中的重点。若后续修改为全局监听，需要重新评估聊天页在多个附件同时传输时的刷新开销。
[修改]平台功能验证需要分别在移动端和桌面端执行。file_picker 在不同平台上的文件路径、权限和取消行为存在差异，flutter_local_notifications 在 macOS、Android 和 iOS 上的初始化方式也不同。测试时应确认文件选择取消不会创建无效消息，通知初始化失败不会中断传输，移动端 toast 和桌面端应用内提示能按平台分支工作。二维码扫描功能也需要考虑设备是否具备摄像头和权限。

## 6.3 性能/稳定性分析

[修改]性能与稳定性分析采用保守描述，不写未经自动化基准验证的吞吐量、耗时和内存峰值。Hydrop 的大文件传输主要依靠 1MB 分片、文件流读取、FrameCodec 帧协议、有限并发和进度节流来降低风险。发送端不会把完整文件一次性读入内存，接收端会把数据分片写入目标文件，目标目录优先为下载目录中的 Hydrop 文件夹。由于 Wi-Fi 路由器、设备存储速度和系统后台限制都会影响结果，本文只说明设计上的稳定性处理，不给出未经基准测试支撑的固定吞吐量。
[修改]稳定性重点关注网络中断、连接超时、确认超时、文件过大、通知插件失败和数据库唯一约束冲突等异常。系统在传输链路中提供错误捕获和状态回写，UI 可根据运行时进度显示 failed、paused、completed 等阶段，数据库附件状态则保存为 pending、transferring、saved 或 failed；应用前后台切换时由运行时管理发现服务和传输服务，减少后台状态不一致问题。
[修改]系统仍可从生产级功能上继续增强，包括更细致的自动化压力测试、跨平台长时间运行测试、复杂网络环境下的重连策略、端到端加密、传输队列优先级、缩略图生成和历史文件清理策略。若后续实现加密传输，可进一步完善密钥协商、身份认证和传输机密性设计。
[修改]大文件传输的性能风险主要来自内存、磁盘和网络。内存风险来自一次性读取完整文件或一次性保存完整接收内容；磁盘风险来自高频进度落库和接收端写入速度不足；网络风险来自 Wi-Fi 抖动、路由器隔离、对端应用进入后台和 TCP 连接中断。Hydrop 通过流式分片读写降低内存风险，通过进度节流降低数据库写入压力，通过失败状态和错误信息减少长时间无反馈等待。由于不同路由器和设备存储速度差异较大，论文不写固定传输秒数，而是描述验证方法和设计依据。
[修改]稳定性分析还需要关注长时间任务。数 GB 的视频文件传输可能持续较久，期间用户可能锁屏、切换应用、移动设备或关闭对端应用。系统必须在这些情况下尽快把状态反映到 UI，而不是让附件卡片一直保持满进度或加载状态。传输进度快照中的 updatedAt、phase 和 errorMessage 可以帮助判断任务是否仍在推进；心跳和确认超时则用于发现连接失效。后续若要进一步接近生产环境，还可以加入更细的队列状态、重连次数、失败原因分类和可视化诊断信息。
[修改]在千兆局域网目标下，单纯增大分片大小并不能解决全部问题。吞吐量还受到 Dart 编码开销、Socket 写入策略、磁盘读写速度、进度刷新频率和 UI 重建范围影响。1MB 分片是性能和内存之间的折中，有限并发 2 可以防止多个大文件互相抢占资源。若后续要继续优化，应通过基准测试分别测量纯文件读取速度、FrameCodec 编解码速度、Socket 传输速度、接收端写盘速度和 UI 刷新开销，再决定是否调整分片大小、引入连接复用或改进缓冲区管理。

[修改]后续可以继续改进几个方向：第一，补充端到端加密和身份认证；第二，增加缩略图生成、历史文件清理和更细的传输队列管理；第三，建立自动化性能基准和长时间稳定性测试；第四，继续探索 mDNS、DNS-SD 等发现方式，提高复杂网络环境下的设备发现成功率。

# 附录 A 中文译文

本附录为与本文系统设计相关的英文技术资料译文整理，内容围绕跨平台界面开发、响应式布局、异步状态管理、本地网络通信、本地数据库和文件系统访问等方面展开。译文用于说明本文所采用技术路线的理论依据和工程背景，正文第 2 章和第 4 章已结合项目代码对相关技术进行了分析。
Flutter 是一种用于构建多平台应用界面的开发框架。它通过统一的渲染体系在不同平台上绘制界面，使开发者能够用同一套代码构建移动端、桌面端和 Web 端应用。与完全依赖平台原生控件的方案相比，Flutter 更强调组件组合和声明式界面构建。开发者通过描述界面在某一状态下应呈现的样子，由框架根据状态变化重新构建对应的 Widget 树。这种模式适合界面状态频繁变化的应用，例如聊天消息列表、传输进度条、设备在线状态和设置项变化等。
在跨平台应用中，响应式布局是界面设计的重要部分。不同设备的屏幕宽度、输入方式和使用姿态并不相同，移动端更适合单栏布局，桌面端更适合多栏布局。响应式设计并不是简单地把控件按比例放大或缩小，而是根据窗口宽度重新组织信息。对于局域网文件传输应用而言，手机端可以先展示设备列表，用户点击设备后进入聊天页；桌面端可以在左侧保留设备列表，在右侧展示聊天内容。这样既能保持移动端操作清晰，也能利用桌面端的横向空间。
Dart 语言提供 Future、Stream 和 async/await 等异步编程机制。Future 用于表示一次异步操作的结果，Stream 用于表示持续产生的数据序列。设备发现、TCP 消息接收、文件传输进度和数据库监听都属于持续变化的数据来源，因此适合用 Stream 或响应式状态封装。通过异步机制，应用可以在等待网络、文件系统或数据库返回结果时保持界面响应，避免因长时间 I/O 操作阻塞用户界面。
状态管理在 Flutter 应用中承担连接业务逻辑和界面的作用。页面本身适合处理临时交互状态，例如输入框内容、焦点和滚动位置；而设备列表、聊天记录、传输进度和系统设置属于跨页面或长期状态，不应完全存放在页面局部变量中。使用独立的状态管理方案，可以让页面只订阅需要的数据，并把业务操作交给控制器、仓库或服务处理。对于文件传输进度这种高频变化状态，按附件 ID 进行精确订阅能够减少不必要的界面重建。
本地网络通信通常会把发现和传输拆分为两个阶段。发现阶段需要找到同一局域网内可用的设备，适合使用 UDP 广播或类似机制。UDP 广播不要求事先知道对端地址，适合发送体积较小的设备公告。由于 UDP 不保证可靠送达，发现公告应周期性发送，并使用超时机制判断设备是否离线。传输阶段则需要可靠、有序的数据通道，适合使用 TCP。TCP 提供连接、顺序和可靠传输基础，适合承载文本消息、文件元信息和文件分片。
TCP 是面向字节流的协议，应用层需要自己定义消息边界。如果直接把多个 JSON 字符串或二进制文件内容连续写入 TCP，接收端无法天然知道一次读取对应哪一条业务消息。因此应用层常使用长度前缀协议：先写入消息头长度和消息体长度，再写入消息头和消息体。消息头可以保存类型、版本、文件名、偏移量、附件 ID 等元数据，消息体可以保存文本内容或文件分片。这样既能处理文本消息，也能处理二进制文件。
文件传输系统需要避免一次性读取完整文件。对于较大的视频或压缩包，如果把文件全部加载到内存再发送，容易造成内存占用过高甚至应用崩溃。更合理的方式是使用文件流按固定大小分片读取，每读取一块就发送一块，接收端也按分片写入目标文件。分片大小需要在效率和内存之间折中，分片过小会增加协议开销，分片过大则会增加单次内存占用和失败重试成本。传输进度可以根据已传字节数和总字节数计算，传输速度可以根据相邻两次进度更新之间的字节差和时间差计算。
本地数据库适合保存需要恢复和查询的结构化数据。设备信息、设备地址、消息、附件、设置和统计信息之间存在明确关系，适合使用关系型数据库。SQLite 是常用的嵌入式数据库，能够在本地应用中提供稳定的数据存储能力。对于聊天和文件传输应用而言，数据库不仅用于保存历史记录，也用于保存失败状态、文件路径、传输进度和用户设置。应用重启后，用户仍然可以看到设备记录、聊天记录和未完成的附件状态。
文件系统和平台能力是跨平台应用不可忽视的部分。文件选择、下载目录、通知权限、摄像头扫描和本地提示都依赖操作系统提供的能力。跨平台框架通常通过插件访问这些能力。插件的作用是把平台差异封装在统一接口之后，使业务层不用直接编写 Android、iOS 或桌面端原生代码。但是平台插件可能受到权限、系统版本或注册状态影响，因此业务流程不能把通知展示、toast 提示等辅助能力视为传输成功的必要条件。即使通知初始化失败，文件传输主流程也应继续执行，并把错误记录到日志中。
从软件工程角度看，局域网文件传输应用适合采用分层架构。表现层负责页面显示和用户操作，应用层负责业务编排，数据层负责数据库访问，基础设施层负责网络、文件系统、通知和二维码等平台能力。分层设计可以减少模块之间的直接耦合，使界面风格调整、协议变更和数据库结构变化不会相互影响。对于毕业设计项目，清晰的分层也有助于在论文中说明需求分析、系统设计和代码实现之间的对应关系。
综上，跨平台 UI、异步流式处理、本地网络通信、关系型数据库和平台插件共同构成了局域网文件传输系统的技术基础。界面层需要根据设备尺寸变化调整布局，状态层需要把发现、消息和传输进度转化为可观察数据，网络层需要区分 UDP 发现和 TCP 传输，数据层需要保存可恢复的业务状态，平台层需要提供文件选择、下载目录和通知能力。这些技术共同支撑了本文系统中设备自动发现、聊天式文件传输、进度反馈、设置持久化和多端适配等功能。

# 附录 B 英文原文

This appendix provides the English technical material corresponding to Appendix A. The material is organized around cross-platform interface development, responsive layout, asynchronous state handling, local network communication, local persistence, and file-system access. These topics are directly related to the design and implementation of the LAN file transfer system discussed in this thesis.
Flutter is a framework for building user interfaces across multiple platforms. It uses a unified rendering model to draw the interface on different operating systems, allowing developers to build mobile and desktop applications from one code base. Compared with approaches that rely entirely on native platform controls, Flutter places more emphasis on widget composition and declarative interface construction. Developers describe what the interface should look like for a given state, and the framework rebuilds the widget tree when the state changes. This model is suitable for applications whose interface changes frequently, such as chat message lists, transfer progress indicators, device online states, and settings panels.
In cross-platform applications, responsive layout is an important part of interface design. Screen width, input method, and usage context differ between mobile and desktop devices. Mobile devices are better suited to a single-column layout, while desktop devices can use a multi-column layout. Responsive design is not merely scaling controls up or down; it reorganizes information according to the available window size. For a LAN file transfer application, the mobile interface can first show the device list and then open a chat page after the user selects a device. On the desktop interface, the device list can remain on the left while the chat content is shown on the right. This keeps mobile interaction clear and makes better use of horizontal space on desktop.
The Dart language provides asynchronous programming mechanisms such as Future, Stream, and async/await. A Future represents the result of one asynchronous operation, while a Stream represents a sequence of values produced over time. Device discovery, TCP message receiving, file transfer progress, and database observation are all sources of changing data, so they are well suited to Stream-based or reactive state handling. With asynchronous programming, the application can keep the interface responsive while waiting for network, file-system, or database operations.
State management connects business logic with the user interface in a Flutter application. A page can manage temporary interaction state, such as text input, focus, and scroll position. However, device lists, chat history, transfer progress, and application settings are cross-page or long-lived states, and they should not be stored only in local page variables. A separate state management solution allows pages to subscribe only to the data they need, while business actions are handled by controllers, repositories, or services. For high-frequency transfer progress, subscribing by attachment ID can reduce unnecessary interface rebuilds.
Local network communication is often divided into a discovery stage and a transfer stage. The discovery stage needs to find available devices in the same LAN, so UDP broadcast or a similar mechanism is appropriate. UDP broadcast does not require the sender to know the receiver address in advance, and it is suitable for sending small device announcements. Since UDP does not guarantee delivery, announcements should be sent periodically, and a timeout mechanism should be used to determine whether a device is offline. The transfer stage requires a reliable and ordered data channel, so TCP is more suitable. TCP provides connection management, ordering, and reliable transmission, which are useful for text messages, file metadata, and file chunks.
TCP is a byte-stream protocol, so the application layer must define message boundaries. If multiple JSON objects or binary file contents are written directly into a TCP connection, the receiver cannot naturally know where one application message ends and the next one begins. A common solution is to use a length-prefixed protocol: write the header length and body length first, then write the header and body. The header can contain metadata such as message type, protocol version, file name, offset, and attachment ID, while the body can contain text content or binary file chunks. This structure supports both text messages and binary file transfer.
A file transfer system should avoid loading an entire file into memory. For large videos or archive files, reading the whole file before sending it may cause excessive memory usage or even application failure. A better approach is to read the file as a stream in fixed-size chunks, send each chunk after it is read, and write each received chunk to the target file on the receiver side. The chunk size should balance efficiency and memory usage. Very small chunks increase protocol overhead, while very large chunks increase memory usage and the cost of retrying a failed write. Transfer progress can be calculated from transferred bytes and total bytes, and transfer speed can be calculated from the byte difference and time difference between two progress updates.
A local database is suitable for structured data that needs to be queried and restored. Device information, device addresses, messages, attachments, settings, and statistics have clear relationships, which makes a relational database appropriate. SQLite is a common embedded database that provides stable local storage for applications. In a chat and file transfer application, the database is not only used to store history; it also stores failure states, file paths, transfer progress, and user settings. After the application restarts, the user can still see device records, chat history, and unfinished attachment states.
File-system access and platform capabilities are also important in cross-platform applications. File selection, download directories, notification permission, camera scanning, and local prompts all depend on the operating system. Cross-platform frameworks usually access these capabilities through plugins. Plugins hide platform differences behind a common interface, so the business layer does not need to directly implement Android, iOS, or desktop native code. However, platform plugins can be affected by permission, operating system version, or registration status. Therefore, auxiliary feedback such as notifications and toast messages should not be treated as required conditions for a successful transfer. Even if notification initialization fails, the file transfer flow should continue, and the error should be logged.
From a software engineering perspective, a LAN file transfer application is well suited to a layered architecture. The presentation layer handles page rendering and user interaction. The application layer coordinates business behavior. The data layer handles database access. The infrastructure layer provides network, file-system, notification, and QR-code capabilities. Layered design reduces direct coupling between modules, so changes in interface style, protocol structure, or database schema do not unnecessarily affect each other. For a graduation project, clear layering also helps explain the relationship between requirements analysis, system design, and code implementation.
In summary, cross-platform UI, asynchronous stream processing, local network communication, relational persistence, and platform plugins form the technical basis of a LAN file transfer system. The interface layer adapts layout to device size, the state layer converts discovery events, messages, and transfer progress into observable data, the network layer separates UDP discovery from TCP transfer, the data layer stores recoverable business state, and the platform layer provides file selection, download directory access, and notification capability. Together, these technologies support automatic device discovery, chat-style file transfer, progress feedback, persistent settings, and multi-device adaptation in the system described in this thesis.

class FrameCodec {
  const FrameCodec();
  List<int> encode(TransferFrame frame) {
    final headerBytes = utf8.encode(jsonEncode(frame.header));
    final bodyBytes = List<int>.unmodifiable(frame.body);
    _validateLengths(headerBytes.length, bodyBytes.length);
    final bytes = Uint8List(8 + headerBytes.length + bodyBytes.length);
    final header = ByteData.view(bytes.buffer);
    header.setUint32(0, headerBytes.length, Endian.big);
    header.setUint32(4, bodyBytes.length, Endian.big);
    bytes.setRange(8, 8 + headerBytes.length, headerBytes);
    bytes.setRange(8 + headerBytes.length, bytes.length, bodyBytes);
    return List<int>.unmodifiable(bytes);
  }
}

class TransferProgressSnapshot {
  const TransferProgressSnapshot({
    required this.attachmentId,
    required this.direction,
    required this.phase,
    required this.transferredBytes,
    required this.totalBytes,
    required this.bytesPerSecond,
    required this.updatedAt,
    this.errorMessage,
  });
  double get progress {
    if (totalBytes <= 0) {
      return 0;
    }
    return (transferredBytes / totalBytes).clamp(0.0, 1.0).toDouble();
  }
