# 01_封面

各位老师好，我的毕业设计题目是基于 Flutter 的跨平台高速文件传输系统设计与实现。这个系统我命名为 Hydrop，核心目标是在同一局域网内，让手机、平板和电脑之间可以自动发现设备，并通过聊天式入口发送文本和文件。今天我会先讲课题背景和需求，再重点介绍总体架构、设备发现、TCP 传输协议和本地持久化设计，最后结合当前程序进行演示。

# 02_研究背景

这个课题来自一个很日常的场景：手机拍了课堂照片，需要传到电脑整理；电脑里的文档要发给另一台设备继续编辑；视频素材也经常需要在多台设备之间移动。常见方案都能解决一部分问题，但并不总是直接。云盘需要先上传再下载，速度受外网上行限制；蓝牙不依赖网络，但大文件传输比较慢；厂商互传体验好，但往往限制在同一生态。Hydrop 选择局域网直连，就是希望在同一 Wi-Fi 或热点环境里减少中转和配置门槛。

# 03_系统目标与成果

因此，我的目标不是只写一个 Socket 发送程序，而是做成一个完整的跨平台应用闭环。第一个目标是跨平台运行，同一套 Flutter 代码适配移动端和桌面端；第二个目标是局域网高速直连，用 UDP 做设备发现，用 TCP 做可靠传输；第三个目标是状态可解释，发送中、失败、完成、进度和速度都能显示出来；第四个目标是本地持久化，设备、地址、消息和附件状态都保存到数据库中。最终程序形成了发现设备、进入会话、发送文本或附件、查看进度和历史的完整流程。

# 04_需求边界

需求设计上，我把系统组织成“设备即联系人”的模式。用户通常不是先想到一个传输任务，而是先想到要把文件发给哪台设备，所以设备列表既是发现结果，也是会话入口。功能需求包括设备发现、会话消息、文件传输、状态反馈和基础设置；非功能需求包括跨平台、可维护、可恢复和异常可提示。这样的边界也让演示流程比较清楚：先选择设备，再进入会话，然后发送文本或附件，最后观察进度和反馈。

# 05_总体架构

系统采用四层结构。最上层是 presentation，也就是 Flutter 页面和组件，例如 HomePage、ChatPage、SettingsPage。中间的 application 层负责编排业务逻辑，比如 AppRuntime、DiscoveryController、FileTransferCoordinator。data 层负责本地数据库、DAO 和 Repository，同时 remote service 负责 UDP、TCP、文件存储和平台能力。core 层放协议常量、主题、工具和日志。这样设计的重点是页面不直接操作 Drift、Socket 或平台 API，而是通过 Riverpod provider 读取状态、触发动作，从而降低耦合。

# 06_设备发现

设备发现使用 UDP 广播。程序在 39175 端口发送和监听 discovery hello，payload 中包含设备 ID、显示名称、TCP 端口、能力列表、nonce 和本机可用地址。LocalNetworkAddressService 会枚举本机网络接口，过滤回环、链路本地和虚拟网卡地址，并尽量补齐网关、子网和广播地址。DiscoveryController 收到广播后会过滤本机设备和重复 nonce，把设备与地址写入数据库，并按 TTL 把长时间未刷新的设备标记为离线。如果广播不可用，程序还提供二维码连接作为补充路径。

# 07_传输协议

文件和文本传输使用 TCP 39176 端口。TCP 本身是字节流，不保证一次读取刚好是一条应用消息，所以我设计了 FrameCodec：前 4 字节是 header 长度，后 4 字节是 body 长度，接着是 JSON header 和 binary body。header 保存帧类型、消息 ID、附件 ID、偏移量等元数据，body 保存文本内容或文件分片。文件传输分为 fileOffer、fileChunk、fileComplete 和对应 ACK，分片大小为 1MB，并通过 SHA-256 校验完整性。

# 08_本地持久化

本地数据库使用 Drift。当前数据库包含设备表、设备地址表、连接会话表、消息表、消息附件表、设置表、本机资料表和统计表。设备地址表记录一台设备的多个 IP、端口、网卡、可达性和测速结果；消息表记录文本内容、方向、发送状态和本地/远端消息 ID；附件表记录文件路径、总大小、已传字节、校验值和传输状态。这样做的好处是状态不会只存在内存里，即使传输失败或应用重启，也可以恢复到一个可解释的状态。

# 09_跨平台界面

界面方面，Hydrop 使用同一套 Flutter 代码适配手机和桌面。HydropAdaptiveBuilder 根据窗口宽度划分 compact、medium、expanded 和 large。手机端使用底部导航和单栏页面栈，点击设备后进入聊天页；桌面端使用左侧导航，并在设备页内部形成设备列表和聊天区域的双栏布局。视觉上程序使用黑白灰、直角和 2px 分割线，减少装饰色，让界面更接近工具型应用。

# 10_核心实现亮点

这里总结五个实现亮点。第一是 AppRuntime，把应用生命周期、发现服务、TCP server 和未完成传输恢复串起来。第二是多网卡发现，尽量让设备在复杂网络环境中仍能找到可用地址。第三是文本 ACK，消息先写入 pending，再根据 ACK 或异常更新状态。第四是 FileTransferCoordinator，统一处理文件协商、分片、完成、校验、暂停、取消和恢复。第五是可测试边界，Repository、协议服务和 Widget 都有相应测试基础。

# 11_测试与结果

测试主要分为四类。功能测试验证设备发现、聊天、文件选择、主题语言和二维码连接等流程；协议测试验证发现 payload、广播服务和 FrameCodec 的边界情况；仓库测试使用内存数据库验证设备、地址、会话、消息等数据读写；组件测试验证图片组件、玻璃组件和页面使用约束。测试结论是核心链路能够运行，主要状态能够被观察和恢复。剩余风险主要在不同平台的网络权限、路由器广播策略和真实多设备环境差异。

# 12_程序运行截图与演示

这一页是演示提示页，后续可以把真实截图放到四个占位框中。现场演示我建议按五步走：先打开两个端，观察自动发现或使用二维码连接；然后进入某个设备会话，发送一条文本消息；接着选择文件或图片进行传输；传输过程中观察进度、速度、暂停或取消；最后回到历史消息和设置页，说明状态和本机资料都已经进入本地管理。

# 13_论文与程序差异

这里我需要主动说明一点：论文是在提交时的程序基础上整理的，而当前源码在提交后又做了一些工程完善。比如传输页源码、暂停取消、自动恢复、通知进度，以及更统一的黑白灰 UI 组件都有进一步改进。答辩时我的口径是：论文重点说明系统设计和核心实现，现场演示展示当前程序的最新状态，这些差异属于提交后的工程完善，不改变课题的核心技术路线。

# 14_总结与展望

最后总结一下，Hydrop 已经实现了一个基于 Flutter 的跨平台局域网文件传输系统，完成了响应式界面、UDP 设备发现、TCP 文本和文件传输、Drift 本地持久化以及状态反馈。它验证了 Flutter 不仅可以做 UI，也可以承担网络密集型应用的主体实现。后续可以继续增强端到端加密、身份校验、多任务调度、后台策略和真实多设备性能测试。以上就是我的答辩内容，谢谢各位老师，请批评指正。
